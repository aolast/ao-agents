# 问题调查

先读目标项目的说明、已有故障材料和当前运行事实，明确调查要回答的问题及可访问环境。已有精确定位的问题可以直接进入修复，不为了形式重复完整排查。

## 环境与观测

描述预期和实际差异、影响范围、频率、时间窗口、版本、配置和数据条件。将用户报告、直接观测和自己的推测分开。

按实际运行时、数据库或 CI 环境选择调查方法，基于可用工具、官方文档和可访问事实开展调查。缺少必要观测能力时说明限制，不假定拥有生产权限或虚构命令、日志和结果。

优先保留可能消失的证据，使用与风险相称的观测手段。重启、修改数据或线上实验可能改变现场；执行前明确目的、影响和已有授权，不能把排查当作任意修改环境的许可。

## 假设与实验

1. 尝试建立最小复现或明确故障与正常样本的差别；无法稳定复现时，保留已知发生条件，不编造复现结论。
2. 提出有依据的候选解释，写清能支持或推翻它的观测。只保持当前有区分价值的假设，不凑固定数量。
3. 优先选择能区分假设、成本低且影响可控的实验；避免同时改变多个相关因素，导致结果无法归因。
4. 对照实验结果更新判断。时间上的先后、错误相关性、单次修复后变好，都不独自证明根因。
5. 区分临时缓解、直接原因与深层成因。能恢复服务的操作不一定解释了为什么故障发生。

证据足以支撑下一项决定时转入行动；权限、样本或观测不足时，交付已有结论和最有价值的下一步，而非无限尝试。

## 结论与衔接

说明现象、支持结论的证据、已排除的高价值假设、剩余未知项以及建议行动。将修复范围、方案及回归验证所需的证据作为后续输入；本次调查不自动启动修复或整套测试流程。

调查很可能跨会话时保存关键证据和当前假设，标明来源与适用环境；不将具体环境的偶然限制上升为通用规则。

## 边界示例

- 发布后错误上升，同时上游也发生故障：应区分两种解释，不直接将发布时间当成回归证据。
- 用户只提供一次超时且没有环境访问：列出能区分客户端、服务端和上游原因的必要信息，不宣称已定位。
