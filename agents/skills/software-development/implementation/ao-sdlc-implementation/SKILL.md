# 软件实现

本 skill 编排实现所需的步骤，按当前问题选择相关能力，复用已有方案与验证证据。先确认目标项目的开发约定、相关实现与现有修改。将设计中的预期行为映射到具体改动，保留不属于当前任务的工作。

实际写入前应用 ao-sdlc-workplace-and-git-branch 的工作区与环境条件；已有明确安排时复用。

## 使用设计与细化实现

开始时核对设计所依赖的接口、仓库能力和关键假设是否适用于当前任务，区分用户／项目的明确要求、已确定的设计决定、示意代码及留给实现的细节。方案清楚且依据仍成立时直接落实，不为形式重新比较方案或完整重审设计；没有正式设计稿也可从明确目标与契约开始，补齐当前需要的决定。

Low-level design 与实现通常交替进行。私有 class/function 的拆分、局部命名和等价控制流由实现者细化；某个决定若改变公开契约、共享规则、状态／资源归属、并发语义或交付范围，就需要按设计决定处理。代码位置小或被称为“实现细节”，不代表影响也小。

| 情况 | 处理方式 |
| --- | --- |
| 设计明确、契约与关键假设成立，具体组织方式可行 | 按设计实现；等价风格偏好不构成重开理由 |
| 草图未固定局部结构，或留下不影响既定约束的细节 | 结合现有代码作出最小合理选择并验证，不逐个函数请求确认 |
| 发现可证实的前提错误、契约冲突、职责错配或明显额外复杂度 | 说明设计意图、具体证据、照做的后果及最小调整，重新判断受影响的决定 |
| 调整会改变用户明确选择、项目硬性要求或关键验收条件 | 在已有授权内处理；需要新的决定时说明具体取舍，暂停依赖该决定的部分，继续不受影响的工作 |

反思应针对证据：例如示意结构造成第二套业务规则，或实例级锁无法保护多个实例共享的状态。“我更喜欢另一种模式”不够。约束内、可逆且影响局部的修正可以直接实施并说明；跨边界或影响重要取舍时，用 ao-sdlc-design 修订相关方案。同步必要的设计说明，避免实现已经改变而后续仍按旧假设工作。

## 实施方法

1. 从可理解、可验证的最小完整修改开始。复用现有合适的机制，避免平行实现同一能力。
2. 逐步完成行为和必要的配套变化，包括调用方、配置和使用文档。源码、生成产物和真实运行环境的状态分别核实。
3. 根据实现证据按上述边界调整相关决定；原因仍不清楚的问题交给 ao-sdlc-investigation，避免叠加未经验证的补丁。
4. 根据 ao-sdlc-testing 确定当前增量与最终交付各需哪些证据及停止条件；复用适用结果，影响变化时更新相关范围。以 ao-sdlc-review 的方法自审有实质风险的变更。

## 编写指导

- **职责与依赖**：业务规则放在清楚的拥有者中；依赖方向与模块边界一致；新增抽象解决已出现的变化或重复需求，不预建通用框架。
- **仓库整合**：先找现有能力及当前有效惯例；职责、契约与生命周期匹配时优先扩展。照搬会破坏契约、塞入无关职责或反向依赖时，比较局部调整与新边界的具体代价；保留能复用的规则并完成接线。旧实现的数量不证明惯例仍适用，也不因局部债务启动全仓库迁移。明确项目要求的变更按上方决策边界处理。
- **可理解性**：命名表达领域含义和单位；控制流清楚；注释解释不明显的约束和理由。不要仅为个人风格改写项目现有惯例。
- **重复与耦合**：优先消除同一知识的多处维护。外形相似但规则独立的代码可以保留分离，避免强行共用导致参数和分支膨胀。
- **输入与状态**：在拥有契约的边界验证输入；区分合法空值、缺失和失败；避免部分更新留下不可解释的状态。
- **失败处理**：错误包含定位所需上下文；不静默吞错或无条件降级为成功。重试、超时、取消和清理沿调用链协调，避免重复副作用。
- **资源与并发**：资源获得与释放有清楚归属；锁、任务、连接与文件生命周期可解释。涉及共享状态时检查并发、取消及异常退出路径。
- **依赖与环境**：新增依赖有具体收益；核实所用版本和接口。避免把机器路径、临时环境假设或凭据写入可分发代码。

仅应用与变更相关的标准，不为无关风险增加层次、分支或配置开关。

## 完成与修正

查看完整差异，确认实现符合目标且没有遗留临时调试逻辑。收到审查问题时先核实条件和依据：成立则修正，不成立则提供反证。按受影响范围复核；若仍存在阻塞，说明缺口，不循环制造修改来满足意见数量。

交付实际行为变化、关键实现理由和验证结果。表达方法使用 ao-sdlc-communication；长期任务的接续使用 ao-sdlc-work-log。

## 边界示例

- 捕获全部异常后返回空列表，会掩盖后端失败：应核实契约并保留可观察的失败语义。
- 两个小函数恰好形似，但分属独立业务规则：不要求为了“消除重复”创建公共框架。
- 已确认的设计要求扩展现有解析器，接口和职责适配：直接实现，不另造解析框架。草图里的三个私有 helper 可以按真实控制流调整；用户明确要求的扩展接口则继续保留。
- 设计用实例内锁避免重复扣款，但实际由多个进程消费同一订单：指出共享边界与锁作用域的冲突，先修订去重方案，不能以“严格按设计”为由继续。
- 现有请求重试器随请求结束而销毁，新需求是持久化后台任务：可以复用重试决策，任务调度按独立生命周期组织；不要为复用强行把后台任务塞入请求对象。
