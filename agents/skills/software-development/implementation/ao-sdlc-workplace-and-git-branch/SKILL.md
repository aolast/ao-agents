# 工作区与 Git 分支

本 skill 定义 coding agent 的开发习惯；仓库的验收要求由项目自身规定。仓库维护或分发此 skill，不代表要求所有贡献者采用其中的工作区布局、分支命名或双分支过程。

## 工作区是什么、在哪里创建

工作区（workplace）是承载一个任务的普通文件夹，用于放置仓库、任务资料及产物。一个工作区可以包含一个或多个仓库；工作区目录本身不作为 Git 仓库根目录，也不直接作为 clone 或 worktree 的目标。仓库的 Git working tree 与这里的任务工作区是不同层级。

未明确指定工作区位置时，默认在当前用户的 `~/workplace/` 下新建 `<任务名>-<agent 或唯一标识>/`。`~/workplace/` 是多个工作区的父目录，每个任务目录才是独立工作区。先确认名称和路径不会占用已有工作；同名目录存在但归属不明时另取唯一名称，不覆盖或接管。

```text
~/workplace/                       # 工作区父目录
└── example-task-agent-a/           # 本任务工作区，普通文件夹
    ├── ao-agents/                 # 仓库 clone 或 Git worktree
    └── artifacts/                 # 按需保存本任务产物
```

另一个仓库需要参与任务时，可在同一工作区内再建并列的仓库目录；资料和产物目录按需创建。先创建任务文件夹，再将仓库 clone 到 `<工作区>/<仓库名>/`，或把 worktree 放到 `<工作区>/<仓库或 worktree 名>/`。不要在工作区根目录执行 `git init`，也不要在那里用 `git clone <来源> .`。

会话、宿主或项目已明确指定工作区及环境时，优先遵循该安排，不强制搬迁已有工作。只有仓库路径时，将其识别为仓库目录，不能据此认定它就是已分配的任务工作区。默认位置不可创建时，说明受限路径，按现有权限机制处理或使用已明确的替代位置；缺少可用位置时询问，不静默改到当前仓库或临时目录。

执行前分别确认工作区路径、仓库路径和仓库基线。Git 命令及依赖仓库相对路径的命令，在工作区内对应的仓库目录执行，例如 `git -C <工作区>/<仓库名> status`；不要把工作区根目录默认当作 Git 命令的工作目录。

## 先确定工作区与环境

在修改文件、安装依赖、运行会写入文件的验证或操作分支前，读取会话、宿主和项目对工作目录与工作环境的明确安排，确认仓库来源、基线、目录归属及允许的操作。已有明确分配和授权时直接沿用，不重复询问。仅提供 cwd、仓库路径或分支名，以及仓库工作树干净，都不代表当前 agent 独占该目录和分支。

- **已明确分配独立工作区与环境**：在分配范围内工作，核实路径和分支后再写入。
- **信息未明确或目录可能共享**：可以先只读定位仓库和基线；默认另建属于本任务的工作区，在其中开发和验证。不要为了腾出当前 checkout 而切换分支、stash、reset、clean 或整理他人的修改。
- **允许使用共享目录**：共享许可本身不包含切换分支或重写当前分支的许可。需要这些操作时，使用自己的 clone 或 worktree；明确约定在同一 checkout 协作时，也须遵守文件和分支的协调范围。

在已创建或明确分配的工作区内部，仓库可采用以下隔离方式；仓库目录名和分支名先确认不会占用已有工作：

| 方式 | 适用与边界 |
| --- | --- |
| 用 `git clone <明确来源> <工作区>/<仓库名>` 创建仓库 | 需要独立的 Git 引用、配置和工作目录，或不宜修改原仓库的 Git 元数据时使用。只在新 clone 中创建、切换或改写本任务分支。 |
| 用 `git worktree add -b <专属分支> <工作区>/<仓库或 worktree 名> <已确认基线>` 添加仓库工作树 | 适合复用本地仓库对象；可从原仓库直接添加，无需先切换原 checkout 的分支。后续 Git 命令在工作区内该仓库目录中执行。 |

Worktree 分离工作文件、HEAD 和暂存区，但共享仓库对象、分支引用及部分配置。先检查 `git worktree list` 和分支归属；不要用 `--force`、`--ignore-other-worktrees`、强制更新引用等方式绕过分支占用，也不要从另一个 worktree 改写、删除或重命名他人正在使用的分支。相同任务由多个 agent 并行时，各自使用不同分支名；独立 clone 也须避免争用同一个远端分支。

新 clone 或 worktree 不自动携带共享目录中的未提交修改。确需以这些修改为输入时，先明确对应版本和差异，再在自己的目录复现。隔离目录也不等于隔离运行环境：依赖、输出和临时文件放在本任务的环境中；复用服务、端口或测试数据前核对环境安排，不能因本机可访问就视为可用。仓库来源或必要环境仍无法确定时，继续可做的只读检查并询问缺失信息。

## 确定分支约定

在归属明确的工作区中读取目标项目的分支规则，确认目标分支、远端与命名空间。采用项目指定的开发与审核前缀；未指定的分别默认为 `dev/`、`review/`，两个分支共用同一任务名。按任务与项目约定确定最终合入的目标分支，通常采用仓库默认分支，并核实实际分支名。若项目明确采用其他分支流程，遵循该流程；工作区与环境的使用仍需符合上述条件。

## 两个分支的职责

| 分支 | 职责 |
| --- | --- |
| 开发分支，如 `dev/<任务名>` | 从最新目标分支创建，承载实现、验证与审核修正；可以按需多次 commit。 |
| 审核分支，如 `review/<任务名>` | 准备送审时从当时最新的目标分支创建，将开发成果 squash 为一个 commit，由此发起并持续更新同一个 PR/CR/MR。 |

单提交要求作用于审核分支。不要为了整理审核历史压缩开发分支，也不要从 dev 的 head 直接创建 review 后保留全部开发 commits。

## 首次送审

1. 在本任务工作区内的仓库开发分支完成实现、提交和必要验证。切换或改写前保留本任务的未提交修改；同名分支存在时先核实任务归属和 worktree 占用。归属不明或被其他 agent 使用时，另取专属分支名，不接管现有分支。
2. 获取最新目标分支，将开发分支 rebase 到该基线，保留本任务的增量 commits。冲突在 dev 上解决并完成 rebase，按影响重新验证。Rebase 会改变 commit ID，但不要求将开发步骤 squash 成一个。
3. 从该基线创建审核分支，用 `git merge --squash <开发分支>` 暂存完整成果，再按项目提交格式创建一个 commit。不要通过 merge dev 的方式把开发历史带入审核分支。
4. 核对下文的送审条件，再推送审核分支并创建审核请求。开发分支是否推送由备份、协作需要及已有授权决定；审核请求使用 review 分支。

例如，项目以 `origin/main` 为目标且使用默认前缀时，以下命令用于已确认由本 agent 独占的工作区、已有开发提交、该仓库工作树干净且审核分支尚不存在的首次送审。每一步均在该工作区内的仓库目录中执行：

```sh
git fetch origin
git switch dev/example-task
git rebase origin/main
# 如有冲突，先解决并完成 rebase；验证通过后继续。
git switch -c review/example-task origin/main
git merge --squash dev/example-task
git commit
```

每步成功后再继续；提交消息采用目标项目格式。任何同步产生的新修改都须先回到开发分支验证，不能只在 review 上修正后就宣布完成。

## 审核返工与更新

在自己的工作区内进入对应仓库，回到原 dev 分支继续开发，用新的 commits 记录修正，再把完整成果更新到原 review 分支。更新前重新确认分支归属和占用；其他 agent 正在使用时先协调，不从另一工作区强行改写。若有人直接修改了 review，先核对差异，把有效改动移回 dev 并验证；不要用旧 dev 快照覆盖这些改动，也不要把 review 的 squash commit 整体合回 dev。

- **目标基线未变**：把已验证的 dev 完整文件树同步到 review 的暂存区与工作区，然后 `git commit --amend`，保留一个审核 commit。同步必须包含删除与重命名。不要假定再次 `merge --squash dev` 会自动识别已送审内容；两条分支没有共享开发 commits，重复 squash 可能冲突。
- **目标分支前进，或不便 amend**：先在 dev 上同步最新目标并验证，再从该基线创建临时候选分支，重新 squash dev 并提交。核对完整 diff、文件树及相对旧 review 的变化后，用候选提交更新原 review 分支，保持原审核请求。改写前保留旧 review 的可恢复引用；候选分支不能通过额外 commit 或 merge 接到旧 review 后面。
- **远端审核分支已有更新**：先读取并检查他人提交，处理后再更新。对已推送分支的改写使用 `git push --force-with-lease`，以检查过的远端 head 为预期值；lease 失败时重新检查，不能改用 `--force` 绕过。

同步目标分支采用 rebase，避免引入 merge commit。共享分支只有在已明确协调改写权限、处理协作者更新后才能 rebase；不强推目标分支。

## 每次送审的条件

记录本次同步后的目标基线与已验证 dev head，检查：

```sh
git merge-base --is-ancestor <目标基线> <审核分支>
git rev-list --count <目标基线>..<审核分支>
git rev-list --merges <目标基线>..<审核分支>
git diff --exit-code <开发分支> <审核分支>
```

这些命令中的参数须替换为实际引用。结果应依次为成功、`1`、无 merge commit、无文件树差异；同时阅读相对目标基线的完整 diff，确认仅包含本任务。只有 commit 数为 `1` 不足以证明内容正确或已跟上目标分支。没有实际差异时无需创建空审核提交。

如果检查后 dev 又有提交，或目标分支前进，重新同步并检查受影响条件。推送后确认审核请求仍指向正确目标，等待 CI 针对最新 review head 通过；不要将 dev 的测试结果误称为审核分支的 CI 结果。

按项目合并策略和既有授权结束审核。

## 合并后清理

清理以单个 code change 范围可控、最终成果已合入目标分支且合并历史保留为前提。之后需要 rollback 时，通过新增 revert commit 撤销变更，原提交及其代码快照仍留在目标分支历史中。后续修改可以基于已合并的成果，从最新目标分支创建新的任务分支继续，无需保留完整开发历史。

- **清理时机**：确认任务成果已经合入目标分支后，及时清理本任务的本地与远端 dev、review 分支，以及改写时创建的临时候选分支和备份引用。开发历史只在任务进行期间保留，不为已完成任务长期保留分支或另建归档分支。
- **交付核对**：获取最新目标分支，核实审核请求的实际合并状态与合并提交；对照最后送审快照确认 dev 的最终成果已交付，没有未提交修改或尚未送审的增量。只合入另一个未进入目标分支的任务分支，不算完成交付。
- **Squash 的判断**：squash 合并不会让 dev 的所有 commits 成为目标分支的祖先，不能只依赖 `git branch --merged`。结合合并记录、最终送审内容和文件树或变更等价性确认成果已进入目标分支；核实后可使用 `git branch -D` 删除仅因祖先关系不成立而无法正常删除的本任务分支。
- **分支占用**：在归属明确且干净的工作区中先离开待删除分支；其他 worktree 正在使用、被未完成任务依赖或存在未交付修改时，先处理该具体问题，不强行清理。
- **远端与残留**：删除前核对远端分支的最新 head，避免删掉核实后新增的工作；平台已自动删除审核分支时，继续清理对应 dev、本地分支与临时引用。最后刷新远端跟踪引用并核对清理结果。

清理目录或 worktree 时也只处理本任务拥有且已保存成果的部分，不移除其他 agent 的工作区。

## 边界示例

- 仓库只要求 PR 恰好一个 commit：采用本 skill 的 agent 可以用双分支保留开发历史；其他贡献者采用不同过程，只要满足项目验收要求，也应正常验收，不能仅因未使用 `dev/`、`review/` 而拒绝。

- 只给出仓库路径，当前 checkout 恰好干净：仍先在 `~/workplace/` 下建立任务文件夹，再在其中创建自己的 clone 或 worktree，不直接在原目录执行 `git switch -c`。
- 已明确分配任务工作区、其中的专属 worktree 和可用测试环境：复用已有安排，不额外 clone 或重复询问。
- 允许读写共享目录，但未授权切换分支：需要在 dev 与 review 间切换时，在自己的工作区执行。分支被另一个 worktree 占用时，换用自己的分支，不加强制参数。
- 项目指定 `work/` 与 `cr/`：使用 `work/example-task` 和 `cr/example-task`；只指定开发前缀时，审核前缀仍可默认 `review/`。
- Dev 有三个实现提交，审核要求修改：在 dev 增加第四个提交，更新后的 review 仍比目标基线多一个 commit，文件树对应第四次开发的完整结果。
- 目标分支增加了与任务无关的文件：先同步 dev，再生成 review；不能用落后 dev 的整棵文件树覆盖新基线，导致该文件被删除。
- Review 已 squash 合入目标分支，dev 最终内容与送审快照一致且没有未交付修改：即使 `git branch --merged` 未列出 dev，也应核实后清理 dev、review 及本任务备份引用。

本 skill 负责任务工作区、其内部仓库的 Git 分支和提交组织；仅为准备工作区而加载时，应用工作区与环境条件即可，不自动启动送审流程。提交表达使用 [how-to-write-commit-message](../../communication/ao-sdlc-how-to-write-commit-message/SKILL.md)，验证深度使用 [testing](../../testing/ao-sdlc-testing/SKILL.md)。它不增加推送、发布评论或合并权限，也不把 Ao Agents 的提交格式和合并责任推广到其他项目。
