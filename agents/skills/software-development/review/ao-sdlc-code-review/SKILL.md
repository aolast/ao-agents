## 简介

按用户指定的范围评审 code changes 及相关需求与解决思路。先确认目标、项目约定、比较基线与待审版本，阅读完整待审材料及必要上下文；PR/CR/MR 覆盖完整 diff，未提交内容另行标明。小变更按实际影响检查。

先建立全局视野，理解背景、动机与解决思路，并核对问题及关键前提；再检查修改范围是否合理，继而评审代码改得是否正确、清楚，最后检查测试能否发现相关错误。前置理解为后续判断提供依据；具体实现正确不能抵消思路与目标的冲突。问题按独立判断组织，已有明确检查对象的条目无需继续拆分。

逐项检查适用问题，状态记为已核实、有问题、待确认或不适用，明确未审范围。未知事实写成假设或证据缺口；核对已有保护与反例，不能仅凭代码形状、模式名称或个人偏好提出缺陷。发现须结合基线说明触发条件、后果及本次改动的影响，按结果模板分类，同一根因只报告一次。

以阅读代码、测试及已有材料为主，仅为澄清具体疑点做最小复现或定向检查。已有依据足够时停止扩查，不默认运行完整测试套件、搭建测试环境或开展性能实验。已有结果须对应待审版本与相关环境；区分静态推断、模拟、真实运行及部署观测，不能用覆盖率、数量或局部通过替代当前判断。复现步骤与关键假设写在对应问题中。

修正复核只检查原问题与受影响部分，证据推翻意见时关闭。Review 产出意见，修改或发布按已有授权执行。

## Checklist / Question List

### 1 背景、动机与解决思路

通过以下 checklist 建立后续评审所需的全局理解。已有问题结合代码与现有证据核实；新增功能结合需求与约束审视思路的合理性。尚无法确认的前提保留为假设，按其对后续判断的影响处理。

- [ ] **1.1** 本次改动的背景与动机是什么？
  说明当前情况及促成改动的需求、机会或约束。

- [ ] **1.2** 本次改动的目标结果是什么？
  说明希望为使用者或系统带来的变化，区分目标结果与实现手段或交付物。

- [ ] **1.3** 有哪些关键的约束、事实、假设？
  区分必须遵守的限制、已有依据支持的情况和仍待确认的前提。

- [ ] **1.4** 当前思路通过什么方式达成目标？
  说明整体处理方式与目标结果之间的关系。

- [ ] **1.5** 支持当前思路的关键前提是否成立？
  核对已有问题的实际表现与可见依据，说明未确认的假设不成立时对判断的影响。

- [ ] **1.6** 这一思路的局限是否与目标或关键约束冲突？
  识别适用边界与无法解决的部分，判断其对本次目标的影响。

- [ ] **1.7** 这一思路带来的代价是否可以接受？
  关注整体处理方式带来的复杂度、资源投入与持续维护负担。

- [ ] **1.8** 相比其他可行思路，当前选择是否合理？
  比较足以影响选择的主要收益与代价，无需穷举替代方案。

### 2 修改范围

按本次目标与所处阶段判断范围，以下典型情形用于定位多改与漏改，是否需要调整须结合实际依赖判断。

- **2.1 有没有多改**
  - [ ] **2.1.1** 新增功能时，是否顺手重构了本次无需调整的既有接口或模块？
  - [ ] **2.1.2** 是否顺手修复了与本次目标无关的旧问题？
  - [ ] **2.1.3** 是否混入了与本次逻辑修改无关的大范围格式化、重命名或文件移动？
  - [ ] **2.1.4** 是否顺带升级了本次并不需要升级的依赖或工具链？

  对这些改动判断是否应拆成独立 PR 或移出本次范围；确属必要前置的重构可以保留，或先独立交付。说明依赖关系，避免拆开必须一起成立的改动。

- **2.2 有没有漏改**
  - [ ] **2.2.1** 重构时，是否遗漏了保持当前生产行为所需的向后兼容代码？
  - [ ] **2.2.2** 修改接口或数据格式时，是否遗漏了本阶段必须同步调整的上下游？
  - [ ] **2.2.3** 修改数据结构时，是否遗漏了已有数据的迁移或转换处理？
  - [ ] **2.2.4** 新增或替换实现时，是否遗漏了使其实际生效的路由、注册或配置修改？
  - [ ] **2.2.5** 修改行为时，是否遗漏了相应测试的新增或更新？
  - [ ] **2.2.6** 改变使用方式时，是否遗漏了必要说明的更新？
  - [ ] **2.2.7** 修改维护源时，是否遗漏了项目要求同步提交的生成产物？

  对缺口判断应将已有配套改动合入本次，还是补充新的改动；允许分步推进时，明确当前可保留的缺口、理由及后续安排，并检查各步必要的正确性与兼容性。不能将当前阶段成立所必需的内容推迟到后续。

### 3 代码实现

围绕具体改动是否正确、清楚展开评审，依次检查功能性与正确性、代码质量与可读性、性能。

#### 3.1 功能性与正确性

- **3.1.1 行为与接线**
  - [ ] **3.1.1.1** 实际入口到返回的执行路径是否满足需求？
  - [ ] **3.1.1.2** 执行产生的副作用是否符合契约？
  - [ ] **3.1.1.3** 实际路由或注册是否指向预期实现？
  - [ ] **3.1.1.4** 调用方传入的参数是否符合新实现要求？

- **3.1.2 边界与表示**
  - [ ] **3.1.2.1** 空值与缺失是否按契约区分？
  - [ ] **3.1.2.2** 输入范围边界是否处理正确？
  - [ ] **3.1.2.3** 集合顺序是否符合要求？
  - [ ] **3.1.2.4** 数值精度是否满足领域规则？
  - [ ] **3.1.2.5** 单位或时区转换是否保持原有语义？
  - [ ] **3.1.2.6** 标识符是否指向正确的实体？
  - [ ] **3.1.2.7** 调用方是否正确解释返回结果？

- **3.1.3 状态与副作用**
  - [ ] **3.1.3.1** 代码是否阻止不允许的状态转换？
  - [ ] **3.1.3.2** 中途失败是否留下不允许的部分更新？
  - [ ] **3.1.3.3** 并发请求是否可能绕过状态或去重检查？
  - [ ] **3.1.3.4** 乱序执行是否遗漏必要操作？
  - [ ] **3.1.3.5** 重试时是否保持同一业务操作的稳定标识？
  - [ ] **3.1.3.6** 重复调用是否产生契约不允许的重复副作用？

- **3.1.4 失败与资源**
  - [ ] **3.1.4.1** 具体错误处理是否将失败误写成正常空结果？
  - [ ] **3.1.4.2** fallback 的实际结果是否符合契约？
  - [ ] **3.1.4.3** 提前返回或异常退出是否释放所持资源？
  - [ ] **3.1.4.4** 取消或超时是否清理相关后台任务？
  - [ ] **3.1.4.5** 重启恢复代码是否正确处理已完成的操作？

- **3.1.5 安全边界**
  - [ ] **3.1.5.1** 不可信输入是否在有效边界完成校验？
  - [ ] **3.1.5.2** 授权检查是否覆盖当前操作的全部可达入口？
  - [ ] **3.1.5.3** 查询与写入是否正确限定租户范围？
  - [ ] **3.1.5.4** 输出编码是否适合目标使用环境？
  - [ ] **3.1.5.5** 日志是否泄漏敏感数据？

- **3.1.6 兼容与环境**
  - [ ] **3.1.6.1** 未要求变化的行为是否保持？
  - [ ] **3.1.6.2** 所用 API 与依赖版本是否在目标环境可用？
  - [ ] **3.1.6.3** 配置读取代码是否兼容承诺支持的配置形式？
  - [ ] **3.1.6.4** 序列化或 schema 实现是否兼容现有消费者？
  - [ ] **3.1.6.5** 迁移代码是否支持设计中的中间状态？

#### 3.2 代码质量与可读性

- **3.2.1 职责与代码组织**
  - [ ] **3.2.1.1** 同一 class/module 是否混入独立变化的职责？
  - [ ] **3.2.1.2** 完成一个局部行为是否需要跨越不必要的文件边界？
  - [ ] **3.2.1.3** 单纯转发的代码层是否承担明确责任？

- **3.2.2 依赖、封装与状态归属**
  - [ ] **3.2.2.1** 具体导入与调用关系是否遵循设计中的依赖方向？
  - [ ] **3.2.2.2** 调用方是否依赖被调用模块的私有实现细节？
  - [ ] **3.2.2.3** 可变状态的读写是否由明确的代码边界管理？
  - [ ] **3.2.2.4** 调用结果是否依赖未在接口中表达的初始化顺序？
  - [ ] **3.2.2.5** 资源的创建与清理责任是否便于沿代码追踪？

- **3.2.3 抽象、复用与规则重复**
  - [ ] **3.2.3.1** 同一业务规则是否在多个位置独立维护？
  - [ ] **3.2.3.2** 复用是否把独立变化的规则强行合并？
  - [ ] **3.2.3.3** 新增抽象是否表达了真实共同规则或变化点？
  - [ ] **3.2.3.4** 直接函数或数据结构是否能以更低理解成本完成同样工作？

- **3.2.4 命名与数据表达**
  - [ ] **3.2.4.1** 名称是否准确表达领域概念？
  - [ ] **3.2.4.2** 名称是否准确表达行为及副作用？
  - [ ] **3.2.4.3** 名称是否掩盖单位或状态差异？
  - [ ] **3.2.4.4** 缩写或泛称是否在当前作用域中造成歧义？
  - [ ] **3.2.4.5** 类型与数据结构是否使不同领域概念容易被误用？

- **3.2.5 控制流、注释与可理解性**
  - [ ] **3.2.5.1** 正常路径是否能沿代码直接理解？
  - [ ] **3.2.5.2** 分支条件是否清楚表达各状态之间的关系？
  - [ ] **3.2.5.3** 错误路径是否能追踪到最终处理位置？
  - [ ] **3.2.5.4** 注释是否解释代码无法直接表达的约束或理由？
  - [ ] **3.2.5.5** 错误信息是否保留定位所需上下文？

- **3.2.6 与现有仓库的整合**
  - [ ] **3.2.6.1** 新代码是否放在承担相应职责的维护位置？
  - [ ] **3.2.6.2** 配置与构建是否沿用适用的现有接入方式？
  - [ ] **3.2.6.3** 采用的仓库惯例是否仍然有效？
  - [ ] **3.2.6.4** 偏离现有惯例的具体收益是什么？
  - [ ] **3.2.6.5** 偏离引入的接入与迁移成本是否值得承担？
  - [ ] **3.2.6.6** 沿用现有做法是否扩大了已证实有害的问题？

#### 3.3 性能

结合实际数据规模、调用频率、执行路径及已有性能要求判断影响。一般不预设必须优化或补充性能测量；可提出有具体依据的疑问与建议，并标明尚未确认的前提。是否构成问题及其等级取决于实际影响，不能仅凭潜在优化空间判为阻塞；有依据的严重资源或可用性后果仍按 P1/P2/P3 标准处理。

- **3.3.1 实际负载与预算**
  - [ ] **3.3.1.1** 有明确性能要求时，改动后的执行路径是否在预期负载下满足要求？
  - [ ] **3.3.1.2** 所依据的数据规模与分布是否代表实际输入？
  - [ ] **3.3.1.3** 所依据的并发与访问模式是否符合实际调用方式？

- **3.3.2 算法与资源代价**
  - [ ] **3.3.2.1** 算法复杂度是否适合实际规模？
  - [ ] **3.3.2.2** 数据结构是否适合实际操作模式？
  - [ ] **3.3.2.3** 是否存在不必要的重复扫描？
  - [ ] **3.3.2.4** 是否存在 N+1 调用？
  - [ ] **3.3.2.5** 是否存在不必要的全量复制？
  - [ ] **3.3.2.6** 关键路径是否引入阻塞或锁竞争？
  - [ ] **3.3.2.7** 队列、缓存或后台任务是否存在无界增长？

- **3.3.3 性能收益依据**
  - [ ] **3.3.3.1** 声称收益时，基线与修改后的测量条件是否可比？
  - [ ] **3.3.3.2** 已有结果是否考虑了预热与波动？
  - [ ] **3.3.3.3** 相关尾部表现是否被平均值掩盖？
  - [ ] **3.3.3.4** 已有测量范围是否足以支持所声称的端到端收益？

- **3.3.4 优化代价**
  - [ ] **3.3.4.1** 优化是否改变了承诺的数据新鲜度或其他行为？
  - [ ] **3.3.4.2** 优化是否将代价转移到其他关键执行路径？
  - [ ] **3.3.4.3** 优化新增的维护成本是否与实际收益相称？

### 4 测试

#### 4.1 测试正确性

检查测试是否验证了应有行为、能够发现相关错误，并产生可信的结果。以阅读测试代码与已有证据为主，沿用简介中的最小验证原则。

- **4.1.1 测试目标与覆盖**
  - [ ] **4.1.1.1** 测试所验证的行为是否对应本次改变的契约？
  - [ ] **4.1.1.2** 正常场景是否覆盖实际使用入口？
  - [ ] **4.1.1.3** 关键输入边界是否被覆盖？
  - [ ] **4.1.1.4** 关键失败后的结果是否被覆盖？
  - [ ] **4.1.1.5** 恢复路径是否被覆盖？
  - [ ] **4.1.1.6** 受影响的跨组件契约是否有相应测试？
  - [ ] **4.1.1.7** 迁移测试是否覆盖必要中间状态？
  - [ ] **4.1.1.8** 局部测试无法证明的关键假设是否有相应验证安排？

- **4.1.2 断言与模拟边界**
  - [ ] **4.1.2.1** 预期结果是否来自独立的需求或契约依据？
  - [ ] **4.1.2.2** 断言能否区分本次相关的正确与错误行为？
  - [ ] **4.1.2.3** 是否复制被测实现来计算预期值？
  - [ ] **4.1.2.4** 是否 mock 掉了真正要验证的逻辑？
  - [ ] **4.1.2.5** 模拟依赖的行为是否符合真实依赖的相关契约？

- **4.1.3 回归能力**
  - [ ] **4.1.3.1** 修复用例是否能够捕获基线中的问题？
  - [ ] **4.1.3.2** 用例是否验证修复后应有的结果？
  - [ ] **4.1.3.3** 本次需要保持的既有行为是否受到回归保护？

- **4.1.4 可靠性**
  - [ ] **4.1.4.1** 时钟与随机性是否受到必要控制？
  - [ ] **4.1.4.2** 测试间的共享状态是否造成相互干扰？
  - [ ] **4.1.4.3** 外部依赖波动是否会造成与被测行为无关的失败？
  - [ ] **4.1.4.4** fixture 是否真实表达所测试的场景？
  - [ ] **4.1.4.5** 测试重试是否掩盖不稳定失败？

#### 4.2 测试代码质量与可读性

对测试用例、fixture、mock 和辅助代码逐项应用 **3.2 代码质量与可读性** 的同一套标准，包括职责、封装、抽象、命名、控制流与仓库整合。结合测试代码的用途判断具体问题，报告时引用相应的 3.2 子项；同时检查以下测试特有的表达与维护问题。

- [ ] **4.2.1** 用例是否清楚呈现前置条件、操作与预期结果？
- [ ] **4.2.2** 断言是否绑定契约之外的私有实现细节？
- [ ] **4.2.3** 重复测试准备是否可以复用现有设施以降低维护成本？

## Results Template

### 分级标准

问题与建议只使用 P1、P2、P3，并按此顺序排列。分级依据是当前上下文中的后果、触发可达性和目标要求；所在层级、文件类型、改动行数与修复成本不直接决定等级。测试代码与实现代码适用同一套代码质量及分级标准。

| 等级 | 具体标准 | 对通过的影响 |
| --- | --- | --- |
| P1 - blocking | 在正常使用或有依据的可达场景下，违反本次必须满足的行为、契约或安全边界；会使核心目标失败，造成不可接受的数据、权限、可用性或兼容性后果。也包括阻碍这些关键判断的具体契约或证据缺口，须明确其阻塞原因。 | 必须解决，不能保留未解决的 P1。 |
| P2 - best to have | 有具体影响、值得在本次解决，但尚未达到 P1：例如有界且可恢复的非核心体验问题、未违反硬性预算的资源浪费、会造成实际维护负担的结构问题或相关测试缺口。已有约束与保护使主要目标仍可成立。 | 默认解决；有具体需求和充足理由时可保留。 |
| P3 - suggestion only | 当前契约、主要行为与维护方式均可接受，建议提供局部清晰度、便利性或小幅效率收益；保留现状没有已知的实质缺陷或明显维护负担。 | 仅供参考，不影响通过。 |

每条发现应能回答以下问题；分级依据写入该条结果，不必另交一份评分表：

1. 哪项具体要求或行为受到影响？
2. 什么输入、调用路径或运行条件会触发它？
3. 触发后会造成什么后果？
4. 已有保护或可用恢复方式是否限制了后果？
5. 为什么这些事实支持所选等级？

低频但可达的数据损坏或越权风险仍可为 P1；高频但无实质后果的表达瑕疵不因此升级。缺少精确频率时描述可达条件即可，不要求为分级另做实验。代码与契约已能建立因果链时，无需先运行复现才能报告。

严重度与判断确定性分别说明。未经支持的假设不能直接写成 P1 缺陷，也不能因未执行验证就把潜在严重问题改称 P3。先核对可见上下文；仍有决定性的未知项时，在关键假设中写清缺什么，以及它如何影响等级或通过判断。关键缺口若列为 P1，应说明为什么现有材料无法支持本次必要判断。

### 常见情形

以下是结合条件的判断示例，不是按关键词自动分级；同类问题可以因具体后果不同而属于不同等级。

| 方面 | P1 - blocking | P2 - best to have | P3 - suggestion only |
| --- | --- | --- | --- |
| 背景、思路与范围 | 方案与明确目标冲突；缺少必需消费者或迁移，导致交付无法使用；设计无法保持关键不变量。 | 方案可完成目标，但混入独立清理而明显增加审查负担，或引入有具体维护成本的多余机制。 | 核心动机与方案已清楚，补充一个例子或阅读提示可让说明更易理解。 |
| 功能与失败处理 | 主要路径返回错误结果；合法输入使核心流程崩溃；超时重试会重复扣款；失败被当作空结果进而触发删除。 | 非核心错误提示缺少可操作信息，但错误状态正确、数据安全且可恢复；不违反必要契约的局部体验问题。 | 行为及错误提示已足够使用，措辞或展示顺序还有小幅改进空间。 |
| 安全与隔离 | 应受限的可达入口缺少必要授权；发生越权跨租户读写；新日志暴露凭据；不可信输入能进入危险执行路径。 | 必要访问控制有效，但本次新增入口的非强制审计信息不完整，增加实际排查成本。 | 现有威胁边界与保护已足够，可选防护仅提供少量额外余量；没有具体收益时不报告。 |
| 性能与资源 | 代表性负载下违反必须满足的延迟或容量要求；无界增长可导致服务失效；热点阻塞使主要流程不可用。 | 已能证明的重复查询、复制或锁竞争造成实际浪费，但在目标规模内仍满足必要预算且后果有界。 | 非热点的局部效率改进，当前规模下无实质影响；不凭未经证实的性能猜测要求修改。 |
| 兼容、配置与发布 | 破坏承诺的公开契约；默认配置无法启动；滚动发布的中间状态不兼容；迁移会丢失数据。 | 兼容与发布路径成立，但非必需诊断信息或操作说明不足，增加可恢复故障的处理成本。 | 已可可靠部署与恢复，增加示例配置或便捷提示可减少少量操作步骤。 |
| 代码质量与可读性 | 单位或身份混淆使必要业务结果错误；隐含状态使合法调用顺序破坏必要契约；结构问题已破坏必要隔离或资源生命周期。 | 同一规则多处维护易发生漂移；职责混杂造成具体修改耦合；命名明显误导理解；无责任的多层转发显著增加追踪成本。 | 局部名称或注释可以更清楚，但现状不误导；两种等价写法之间的偏好通常无需报告。 |
| 测试正确性与依据 | 关键行为或迁移安全性无法从现有材料判断，所给测试又替换掉了关键逻辑；必须明确缺口如何阻碍本次目标。 | 实现可从代码与契约判断正确，但遗漏相关回归用例；fixture 不稳定，导致测试结果不可信。 | 已有检查覆盖本次关键风险，再加相邻用例只有少量增益；不按覆盖率或用例数量凑建议。 |

同一问题随证据变化可调整等级，但必须说明后果或前提发生了什么变化。P2 被允许保留后仍是 P2，不改标 P3；修复困难、时间紧或作者不愿修改，也不能把 P1 降级。

### 通过条件与问题归属

最终结论只有“通过”与“未通过”。默认要求本次评审范围内的 P1、P2 全部解决；有具体需求和充足理由时，可以放宽为 P1 全部解决，并在结果中明确保留的 P2、放宽的需求与理由及其影响。P1 不能放宽。不满足所采用的条件时，结论为“未通过”。关键假设尚不清楚、导致无法判断是否满足通过条件时，同样给出“未通过”，说明缺少的依据，不把假设写成已证实缺陷。Review 通过表示本次评审满足这些条件，不代表测试或上线验收通过。

每条发现先选取可比业务场景，对照基线与修改后的输入、环境及调用路径差异，再说明归属及关联方式：

| 归属 | 需要说明的上下文 |
| --- | --- |
| 新引入的问题 | 基线中不存在该问题，本次具体修改如何使其产生。 |
| 既有问题：与本次改动无关 | 基线中已存在，本次没有改变其逻辑、影响或触发条件。 |
| 既有问题：直接关联 | 本次直接改变了问题逻辑或后果，说明问题被减轻、加重或仍然存在的具体表现。 |
| 既有问题：间接关联 | 问题本身已存在，本次通过调用方式、流量、时序、输入或暴露面等变化，增加或减少了触发可能性。 |

直接影响和间接影响可以并存，分别说明，不强行归为一种。仅有相关性不足以证明因果；缺少基线或调用证据时写明未知项。新增入口使旧缺陷更容易触发时，应区分旧缺陷与新增触发路径，不将整个缺陷说成新引入；没有数据时不编造概率数值。

无关既有问题可作为背景或单独记录，不计入本次通过条件。改动减轻问题或降低触发可能性时，应说明改善与剩余影响，不能将改善当作回归；若剩余问题仍阻碍本次目标，须指出具体未满足的要求。P1/P2/P3 根据当前后果与本次目标判断，不由“新问题／旧问题”标签直接决定。

按以下模板交付，替换提示内容。背景只保留帮助理解结论的摘要，无需逐项抄录 checklist。每个问题引用具体子问题编号，同一根因只列一次；测试代码质量问题引用 3.2 的对应子项并标明测试代码位置。尚未形成缺陷判断的疑问写入关键假设或待确认事项，说明其对结论的影响，不为分级而将疑问写成已证实的问题。复现字段写清前置条件、输入或操作、预期与实际结果，并标明是否实际执行；未执行时只描述推断，不声称已复现。关键假设写清依据、确认状态及不成立时对判断的影响。无适用复现步骤或假设时省略对应字段；没有问题时删除示例条目，不为填模板制造问题。
