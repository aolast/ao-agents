# Repo Integration

判断改动是否接入仓库已有的职责、能力和工作方式，以及偏离现状的收益是否足以承担代价。“已有”是调查入口；最终依据是契约、责任归属、实际适用性和维护成本。

## 建立仓库依据

阅读相关项目约定、模块边界说明和实际调用链；寻找承担同类职责的模块、当前维护的相邻实现、公共能力及测试设施。范围围绕本次能力展开，避免仅凭一个旧文件或代码出现次数推断全仓库惯例。

区分明确要求、已记录的演进方向、持续采用的惯例及历史遗留。文档与代码不一致时核对适用范围和迁移状态；仅有旧实现不能证明它仍是推荐方向。没有决策记录时，依据可见契约与影响分析判断，并标明未知项。

## Follow / 不 Follow 的判断

先确认惯例有效，再核对它在当前业务语义、职责、生命周期、依赖方向和失败行为下是否适用，最后比较两种选择的成本。两种选择都要有依据，偏离还应解释新增的不一致与迁移成本。

| 条件 | 判断方向 |
| --- | --- |
| 当前惯例适用，无具体缺陷，复用能降低理解与维护成本 | Follow |
| 差异仅是 reviewer 的措辞、排版或等价实现偏好 | Follow，不据此制造重构 |
| 已有缺点不影响本次目标，改变需要大范围迁移 | 可以局部沿用，同时限制债务扩散 |
| 照搬会破坏正确性、隔离性或必要契约 | 不照搬；明确冲突与必要修正 |
| 扩展会塞入无关职责、大量特例或反向依赖 | 考虑新边界，说明复用部分与接入方式 |
| 已有明确迁移方向，旧模式仍占多数 | Follow 已确认的迁移目标及其适用范围 |

区分外部契约与内部实现：保留 API、配置和领域术语的兼容性，同时改善内部结构。只有风格偏好时不偏离；证据不足时列明未知项，不能靠“仓库一直如此”或“这是技术债”结束判断。

## 选择扩展方式

对实际有竞争力的选项作简短比较，重点是职责匹配、耦合、迁移和验证成本；不要求每次列全所有选项。

| 选择 | 适用依据 | 重点核对 |
| --- | --- | --- |
| 复用或扩展现有 module | 同一领域职责、规则拥有者和生命周期，现有契约能容纳需求 | 是否沿用已有配置、错误处理和测试，避免第二套规则；扩展是否反而塞入独立业务特例 |
| 先局部重构再扩展 | 现有结构确实阻碍当前需求，且局部收敛可解决 | 行为保持边界、受影响消费者、验证办法，以及重构是否值得独立成一个 bundle |
| 新增 module 或机制 | 存在不同职责、信任或生命周期边界；复用会造成反向依赖、破坏契约或显著条件膨胀 | 新边界如何接线，规则拥有者是否仍清楚，哪些旧能力被复用，是否形成平行实现 |
| 暂时沿用现状并限制扩散 | 局部问题不影响本次正确性，替换的迁移或验证成本超过当前收益 | 本次能否避免新增债务消费者、保持接口边界，并记录具体限制；不能据此延续已证实会破坏本次契约的做法 |

仅为“保持一致”复制已证实有害的做法，或仅为“更干净”建立第二套机制，都需要重新评估。可以在现有公共契约内改善内部实现，也可以用边界适配接入新实现；迁移不必等同于全仓库改写。

## 何时偏离现有惯例

先说明当前惯例在本次场景中造成什么：重复维护同一规则、破坏不变量、迫使业务特例进入错误层、扩大共享状态，或已有故障与维护成本等。旧、复杂、非主流或没有采用 reviewer 偏好的模式，本身不能证明技术债。

再比较遵循与偏离的后果：新做法能否解决具体问题，会新增哪些消费者迁移、兼容、接线和维护成本，现有需求是否足以支持这个取舍。正在进行的迁移优先检查新改动是否符合已确认的目标边界；临时双轨要有明确的规则归属、使用范围和退出条件。

项目明确要求与拟议方案冲突时，把必要例外或规则调整列为待确认决策；不把 reviewer 的判断当作已批准的架构变更。仅涉及非强制惯例时，可以给出有证据的偏离建议，无需因惯例不同自动要求额外审批。

## Checklist

- [ ] **现有能力调查**：是否找到同类能力、规则拥有者和实际消费者？声称“没有可复用模块”或“必须沿用”的依据是什么？
- [ ] **职责适配**：扩展现有 module 是否仍符合领域、生命周期与依赖边界？新增 module 是否有可解释的独立责任？
- [ ] **规则归属**：是否引入第二套解析、校验、配置、重试或状态管理？同一事实会不会在不同入口分别维护？
- [ ] **接入完整性**：路由或注册、依赖注入、配置、错误与日志、构建分发及测试设施是否按实际项目方式接入？新增实现是否真正被使用？
- [ ] **惯例有效性**：依据是明确约定、活跃实现还是遗留路径？文档、代码与迁移方向的冲突是否被解释？
- [ ] **技术债依据**：所谓债务是否有具体影响？本次是在继承局部限制、扩大影响面，还是解决当前阻碍？
- [ ] **替代方案成本**：复用、局部重构和新边界中，哪些适用？选择是否同时考虑新增复杂度、消费者迁移和验证成本？
- [ ] **共存与退出**：需要新旧机制并存时，谁使用哪一套，如何保持兼容，何时结束过渡？无法明确退出时，是否有长期双轨的合理责任划分？
- [ ] **范围约束**：必要调整是否保持最小完整范围？是否为了本次局部改动要求清偿无关债务？

## 输出依据与案例

对有争议的整合选择，指出当前拥有者或相关实现的位置、推荐选择及理由、最有竞争力的替代选择的具体代价。不需要为每项无争议复用撰写设计文档。

- 已有 `RetryPolicy` 统一超时与取消，新客户端另写 sleep 循环：若契约相同，优先扩展原策略；指出双套策略导致的具体不一致。
- 现有交互请求重试器持有请求生命周期，新需求是持久化后台任务：先检查重试决策是否可复用；任务调度可有独立 module，不能因都叫“重试”强行共用生命周期。
- 一个旧 `utils` 文件承载多个无关职责：新增领域规则不必继续塞入它；按清楚边界放置新能力，也不必搬迁全部旧代码。
- 仓库正从全局客户端迁移到注入的客户端：先核对迁移约定与目标消费者，再评审新代码；不能仅因全局客户端使用次数更多而要求继续采用。
- 拟议新模块没有错误隔离或职责收益，仅为避开现有文件而复制校验：要求解释实际收益；不能把新文件本身当作更好的结构。
