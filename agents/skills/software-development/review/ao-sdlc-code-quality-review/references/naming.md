# Naming Checklist

从调用者视角核对名称承诺与实际行为，结合本领域术语、作用域和公开契约判断。若名称影响正确使用或理解，应说明具体误导；纯粹等价的措辞偏好可不报告。

- [ ] **领域与角色**：同一概念是否采用一致术语，不同概念是否被同名混淆？同一类型承担不同角色时，名称是否体现角色而非强求统一？
- [ ] **行为与副作用**：函数名是否反映实际操作？`get`、`validate` 等名称是否掩盖写入、创建或破坏性操作？判断需结合项目已约定的语义。
- [ ] **单位与语义**：时长、金额、比例、时区及标识符种类是否能从名称、类型和上下文准确理解？跨接口传递时是否存在单位或身份混淆？
- [ ] **状态与集合**：布尔值、可空值、枚举、单复数及集合名称是否准确表达状态与内容，避免双重否定、含糊 flag 或把缺失当成失败？
- [ ] **抽象与作用域**：module/class 名称是否表达真实责任？`Manager`、`Helper`、`utils` 或缩写是否在此处隐藏领域含义？短循环变量可以合理，长名字也不自动更清楚。
- [ ] **仓库惯例**：是否沿用该模块有效的领域词汇和命名约定？不同子系统是否存在有意区分，名称冲突是否只是历史遗留？
- [ ] **改名代价**：公开 API、序列化字段、配置、命令、动态注册和生成来源是否受影响？建议改名时是否考虑兼容、消费者及迁移范围？

例如，返回毫秒的 `timeout_seconds` 应纠正语义；局部 `i` 无需机械扩写。历史公开字段拼错但仍被外部消费者使用时，可在内部使用清楚名称并保留边界映射，评估兼容迁移后再改公开名称，不能仅为 naming 清晰破坏契约。
