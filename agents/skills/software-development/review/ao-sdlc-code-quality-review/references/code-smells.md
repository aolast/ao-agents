# Code Smells 与 Anti-pattern 评审

Code smell 是值得追查的信号。只有能说明当前场景中的具体危害，才能形成问题；识别到形状相似的代码还不足以要求重构。Anti-pattern 也须结合适用条件与后果判断。

## 评审方法

明确用户要看的是本次差异还是指定模块的整体健康状况，并记录版本。结合调用方、业务规则、状态和生命周期检查下表。计数、搜索和静态分析用于定位候选，报告前核对上下文及合理解释。

每个候选按“模式信号 → 触发条件 → 后果 → 已有保护或反例”验证。区分当前变更引入、加重及既有问题；只做差异评审时，不把无关既有债务变成本次必改项。

## Checklist

表中“报告依据”是需要验证的因果，“合理解释”用于检查反证；两者都不能仅凭名称成立。

| 检查 | 模式信号与报告依据 | 需要核对的合理解释 |
| --- | --- | --- |
| [ ] 职责混杂 | 同一对象因多个独立原因变化，业务、存储或任务生命周期相互干扰；指出具体耦合路径 | 清楚的事务入口或流程协调器可以串联多个步骤 |
| [ ] 修改散落 | 同一规则在多处维护，一次修改容易遗漏消费者并产生不一致 | 外观相似但独立演进的规则可以分别维护 |
| [ ] 错误抽象 | 通用层塞满业务开关和特例，使一个消费者的变化影响其他消费者 | 稳定协议或确有多个实现的边界可以需要适配层 |
| [ ] 过度间接 | 多层转发没有承担转换、契约或生命周期责任，却增加追踪和修改成本 | 兼容 facade、审计、隔离外部 API 可以承担明确责任 |
| [ ] 穿透与循环依赖 | 调用者访问多层内部对象、绕过拥有者或形成环，破坏不变量或独立演进 | 显式只读投影和受控组合未必破坏封装 |
| [ ] 隐式状态与时序 | 可变全局、隐含初始化顺序或魔法 flag 导致调用结果依赖不可见历史 | 有清楚所有权和生命周期的进程级状态可以合理 |
| [ ] 分支与参数膨胀 | 深层嵌套、多个布尔参数或复制条件让状态组合遗漏，难以核验 | 有限状态机、解析器和协议分派可能天然需要分支 |
| [ ] 数据语义丢失 | 字符串、数值或字典混用领域概念、单位和状态，导致非法组合或误传 | 局部且不跨语义边界的数据不一定需要包装类型 |
| [ ] 失败被隐藏 | 捕获全部异常、静默 fallback 或返回空值，使消费者误判成功或覆盖数据 | 契约允许的 best-effort 行为，且失败有相应观测和后果约束 |
| [ ] 生命周期与并发补丁 | 复制重试、随意 sleep、遗漏清理或无界后台任务，引起重复副作用、泄漏或竞争 | 有上限且与幂等、取消和清理机制协调的重试可能必要 |
| [ ] 测试脆弱或失真 | 过度 mock、复制实现算预期值、绑定私有调用，使错误行为仍通过或合理重构必然失败 | 针对关键外部协议的交互断言可以直接表达契约 |
| [ ] 遗留机制 | 无消费者的抽象、失效配置、不可达分支继续增加维护负担或误导使用 | 兼容窗口、动态注册和生成代码需先核实真实使用方式 |

## 输出与取舍

只报告有证据的影响，包含位置、信号、实际条件、后果和最小改进方向。修正收益与改动成本不明确时，可列为非阻塞建议或待确认项。用户要求排技术债优先级时，再按影响、出现频率、继续扩散的可能性和修正成本排序。

对容易误判的重要候选，简述为何保留当前实现；无需列出所有未命中的模式。不设 findings 配额，不因函数长、class 多、用了 switch 或存在重复形状而直接要求重写。

仅识别到 smell 时不能宣称发现了运行时 bug，也不能以 smell 名称代替安全、正确性或维护成本的具体证据。

## 判断边界

- 两段折扣计算形似，但分别遵循独立合同规则：不建议只为去重合并；若它们实际上实现同一合同条款，再检查规则漂移。
- 导出报表是 best-effort，失败写入状态且调用方显示部分失败：不能仅凭捕获异常认定吞错。
- 稳定兼容层只有简单转发：核对兼容责任；删除后会破坏消费者时，不能称为无用层。
