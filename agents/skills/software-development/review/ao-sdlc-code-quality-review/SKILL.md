# Code Quality Review

判断实现是否清楚、职责合理、融入仓库并具有与需求相称的维护成本。Class、module、层数和长度由职责、状态归属、生命周期及变化原因决定，不设通用数量门槛。

## 评审方法

确认目标、项目约定、基线与待审快照，或用户指定的既有模块范围。阅读差异及必要调用方、规则拥有者、相邻实现和测试。具体修改建议应解释它解决的理解障碍、耦合或维护负担；个人风格偏好不足以构成问题。

按对象读取本 skill 内的参考清单：

- 检查标识符与领域术语时，读取 [Naming](references/naming.md)；完整质量评审包含命名检查。
- 完整质量评审读取 [Repo integration](references/repo-integration.md)，核对现有能力与规则归属；新增模块或偏离惯例时深入比较选择。
- 用户要求 smell 扫描或发现可疑模式时，读取 [Code smells](references/code-smells.md)，用合理反例核实其实际影响。

用户只要求 naming 等单一维度时，限定在该维度及必要上下文。遇到已证实的行为缺陷时保留证据与后果，不因其超出主要关注点而遗漏。

## Checklist

逐项记录已核实、有问题、待确认或不适用；未检查不能记为通过。

- [ ] **职责与内聚**：class/module 是否有清楚的职责、状态和变化原因？拆分是否降低理解成本，还是增加无效跳转？
- [ ] **依赖与封装**：依赖方向是否符合边界？是否循环、穿透内部对象或依赖隐含全局状态？接口是否暴露过多消费者不需要的细节？
- [ ] **抽象与重复**：抽象是否对应实际共同规则或变化点？是否复制同一知识，或把独立规则强行合并成参数与分支膨胀的公共层？
- [ ] **实现与选型**：算法、数据结构和依赖是否适合实际规模与维护环境？新增库或通用机制是否有具体收益，是否存在更简单的现有能力？
- [ ] **状态与生命周期**：状态、资源和错误处理的拥有者是否清楚？维护者能否追踪获得、更新、释放及失败处理，而不依赖隐藏时序？
- [ ] **Naming**：是否完成参考清单中的领域、行为、单位、状态、作用域和兼容性判断？
- [ ] **Repo integration**：是否找到现有规则拥有者，核实惯例有效性与适用性？复用、局部重构或新边界的收益是否足以承担成本？
- [ ] **可理解性**：控制流能否表达领域行为？注释是否解释实际约束和理由？定位失败所需的上下文是否便于找到？
- [ ] **测试可维护性**：测试是否围绕契约组织，复用合适 fixture，并避免耦合无关私有细节？合理重构是否会迫使大量无意义的测试改写？
- [ ] **Smell 核实**：可疑模式是否有具体影响，是否检查合理解释？改进是否与收益相称，是否引入无关重构？

## 输出与复核

给出位置、具体结构或使用场景、维护或理解成本、依据和最小改进方向。结构问题要举出职责冲突、调用耦合或修改散落；“应再抽一层”“最好用三个 class”不足以构成发现。

沿用项目严重度标准，区分阻塞问题、非阻塞建议和待确认项，阻塞需说明实际影响。检查反证，区分本次引入、加重及既有问题；无关既有债务不成为本次必改项。合并同一根因，不要求固定 findings 数量。

标明版本、已审维度和限制。修正后复核原问题与受影响结构，证据推翻意见时关闭；实施重构与发布意见按用户已有授权执行。

## 判断边界

- 几个无状态纯函数已清楚表达规则：无需为面向对象形式增加 class。
- 对象同时控制业务决策、数据库连接和后台任务退出，生命周期相互干扰：指出具体耦合路径，再讨论拆分。
- 当前实现与惯例不同但职责明确、接入完整且有实际收益：核实成本，不仅凭“不一致”要求改回。
- 测试绑定无关私有调用，合理重构会大量改写断言：说明维护负担；若测试还漏掉了错误行为，同时保留行为证据供整体结论去重。
