# Code Change Scope 评审

判断送审范围能否被可靠理解和核验，提出最小且完整的交付划分。Scope 既可能过大，也可能因缺少调用方、测试或迁移而不完整。

Logical bundle 是围绕同一目的、能够连贯解释并核验结果的一组 code changes。每组应明确依赖和完成条件；它可以包含多个文件，不必对应一个 commit、一个目录或一个 review request。

## 建立改动地图

明确基线、送审 head、未提交部分和送审目标。单个 commit 以其实际比较基线为准；review request 以完整送审 diff 为准，不能遗漏其中的其他 commits。阅读完整差异，按行为与动机分组：需求变更、必要结构调整、机械修改、生成结果及验证配套。对每组记录涉及内容、为什么需要、依赖与验收办法；分类服务于理解，不预先要求每类单独交付。

检查调用链、配置和迁移等必要上下文，判断各组是否可以独立接受、延后或回退。代码行数、文件数和 reviewer 所需上下文是排查线索，结论必须说明具体认知负担、验证缺口或耦合风险。

## Checklist

逐项记录已核实、有问题、待确认或不适用；未检查不能记为通过。

- [ ] **共同目的**：能否用一个明确目标解释送审内容？每组变化对目标是否必要，还是可以独立取舍的附带工作？
- [ ] **范围完整性**：行为变化所需的调用方、测试、配置、生成来源、说明和兼容处理是否齐全？是否将必须同时成立的内容遗留到未确定的后续？
- [ ] **规则耦合**：哪些修改必须一起接受才能维持不变量？按文件、层或作者拆开后是否反而隐藏跨边界行为？
- [ ] **审查负担**：reviewer 需要同时掌握多少领域、行为分支和契约？是否可提供明确阅读顺序、关键入口和证据，或必须缩小送审范围？
- [ ] **噪声与语义**：格式化、重命名、搬迁或生成差异是否掩盖行为变化？分离后能否明显改善核验，代价是否合理？
- [ ] **前置重构**：结构调整是否确实使本次行为变化可行或更易验证？能否独立证明行为保持，再交付功能变化？
- [ ] **技术债关联**：清理是否解决当前阻碍或本次继续扩散的问题？独立技术债是否可以延后而不损害目标？
- [ ] **过度拆分**：是否把实现与必要回归测试、契约与消费者、源码与必要生成结果拆到无法独立验收的单元？拆分收益是否大于协调成本？
- [ ] **依赖与中间状态**：每组的前置条件、集成顺序和验证边界是否明确？各步骤是否可构建并保持承诺的行为，暂不启用的能力如何约束？
- [ ] **发布与恢复**：review 分组、合入顺序和发布单元是否被混为一谈？依赖存在时能否按顺序发布与恢复，哪些步骤必须协同完成？
- [ ] **项目约定**：拆分建议是否符合目标仓库的 commit、评审和合并规则？是否错误地用 commit 数证明逻辑范围合理？

## 输出与拆分建议

标明已审版本、覆盖范围和材料限制，沿用项目严重度标准，区分阻塞问题、非阻塞建议和待确认项。

给出“范围合理”“保持一起但需改善审查材料”“建议拆分”或“缺少必要配套”的结论及依据，允许组合适用结论。有关键材料缺失时说明暂不能判断。

建议拆分时列出每个 bundle 的目的、具体包含内容、前置依赖、验收证据及中间状态。再说明阅读、合入与发布顺序；这些顺序可以不同。无需为每组强行创建分支或 commit。

推荐分组可以写成：

| Bundle | 包含内容与目的 | 依赖 | 验收及中间状态 |
| --- | --- | --- | --- |
| 统一解析入口 | 收敛旧入口及行为保持测试，使规则只有一处维护 | 无 | 旧接口兼容，既有解析行为不变 |
| 增加新格式 | 新格式解析、入口接线与对应回归测试 | 统一解析入口 | 新旧格式分别满足契约 |

若无法给出保持必要不变量的拆法，应解释保留整体的理由，并指出怎样改善阅读顺序或验证。审查意见本身不执行拆分或改写历史。

## 判断边界

- 大量生成文件随同一 schema 更新，生成来源、消费者和再生成证据明确：规模大不自动意味着 scope 过大。
- 十几行同时改变登录策略与账单规则，二者可独立接受：规模小仍可能应拆分。
- API 兼容层和消费端必须同时满足一个新契约：可以合为一个 bundle；可滚动迁移时则明确兼容窗口后分步。
- 功能依赖行为保持重构：可以建议先重构后功能；不要仅为分层整齐，把功能实现与其必要测试拆开。
