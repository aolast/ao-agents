# 系统设计评审

判断方案能否在目标环境中满足需求，以及关键取舍是否有依据。评审对象可以是设计稿，也可以是代码中体现的系统设计；class 数量和文件拆分只在影响系统边界时进入本评审。

## 评审方法

从需求、现有系统、约束和设计版本建立上下文，画出或用文字追踪入口、组件、外部依赖及数据归属。对照一条正常链路和相关的关键失败链路验证方案；未知条件列为假设，并说明什么证据会改变判断。

对有实质取舍的选择，比较能满足需求的更简单方案及当前方案的代价。已确定的技术或产品约束作为输入；发现冲突时指出冲突及影响，不擅自替换目标。审查深度由后果和未知项决定，小变更无需制造正式设计文档。

## Checklist

逐项按已核实、有问题、待确认或不适用判断；条件项仅在对应风险存在时检查。未检查不能记为通过，缺少关键契约时说明待确认条件。

- [ ] **目标与验收**：需求是否能用可观察结果表达？非目标、不变量、兼容约束及成功标准是否一致？方案是否解决了目标问题？
- [ ] **系统职责**：每项业务规则、状态和资源是否有明确拥有者？服务或组件边界是否符合实际变化、故障与部署边界？是否存在循环依赖或多方同时维护同一事实？
- [ ] **概念与契约**：系统中的领域名称是否一致表达概念与责任？输入、输出、错误、版本和调用顺序是否足以供消费者正确使用？受影响消费者和兼容窗口是否明确？
- [ ] **数据模型与生命周期**：数据的来源、身份、写入权限、保留和删除是否可解释？新增缓存、索引或副本后，谁负责一致性与修复？
- [ ] **一致性与并发**：跨进程或多写入者场景下，事务边界、重复、乱序、冲突及部分成功如何处理？关键不变量是否在实际执行边界成立？
- [ ] **失败与恢复**：依赖超时、不可用、重启后系统呈现什么状态？重试是否与幂等、取消、退避及恢复机制协调？降级结果是否符合契约？
- [ ] **信任与数据边界**：谁可以调用、读取或修改哪些资源？身份、租户和敏感数据是否跨越新的边界？授权及审计责任是否有明确归属？
- [ ] **容量与成本**：代表性负载、数据规模及增长假设是否支撑方案？是否存在无界队列、放大调用或明显瓶颈？性能目标是否有验证办法？
- [ ] **运行与定位**：需要哪些状态、指标或错误信息才能判断失败并采取行动？部署、配置与运维责任是否明确？
- [ ] **迁移与演进**：涉及新旧版本共存时，发布顺序、中间状态、数据迁移及失败处置是否可行？不可逆操作是否有恢复或向前修复方案？
- [ ] **现有系统整合**：相关能力是否已有清楚拥有者？扩展现有边界、局部调整或建立新边界的选择，是否基于职责与实际成本？偏离惯例是否有具体问题和迁移依据，沿用是否扩大已证实的技术债？
- [ ] **方案代价**：新增服务、中间层、依赖或通用机制解决了哪项当前需求？其复杂度与运维成本是否合理，关键替代方案是否被真实约束排除？
- [ ] **可验证性**：什么证据能验证关键假设、兼容性和失败语义？设计阶段是否有可执行的验证计划，已有实现时是否有对应证据？

## 输出

给出方案是否可继续推进、所需条件和关键未决事项。发现应指向设计章节、契约或系统链路，说明触发场景、被破坏的约束、后果及证据；材料不足时作为待确认项。对需要取舍的问题给出有依据的方向，不把另一种个人偏好写成必改方案。

标明版本、已覆盖链路和未验证假设，区分阻塞问题、非阻塞建议和待确认事项；沿用项目严重度标准并说明判断依据。测试计划可支撑方案的可验证性，不能充当方案已经在运行中有效的证据。

核对可能推翻意见的约束、已有保护和作者解释；同一根因合并报告。修正后只复核原问题及受影响部分，新证据推翻意见时关闭。评审产出意见，方案修改与外部操作按用户已有授权执行。

## 判断边界

- 单进程本地工具没有远程调用和共享写入：分布式一致性、服务发现等项可不适用。
- 支付请求超时后自动重试，但没有稳定业务标识或去重契约：追踪提交成功、响应丢失、再次提交的链路，报告重复副作用风险。
- 为明确的租户隔离和独立发布需求引入服务边界：检查代价与验证，不能仅因“服务数量增加”否定方案。
