# 分层 Review 编排

组织系统设计和代码改动的分层评审。四个专项可独立使用；本 skill 负责确定范围、选择层级、合并发现与修正复核。实现与评审是不同活动；实现后自审使用同一套评审标准，自审本身不等同于独立第三方审查。

## 建立审查视图

确认目标、项目约定和对象：设计稿、review request、commit、未提交变更或指定模块。设计稿记录版本及系统约束；代码记录目标基线与实际 head，未提交内容另行标明。一个 PR/CR/MR 可以包含紧密相关的多个 code changes；提交数量不代表逻辑范围合理。

设计评审阅读完整方案及相关系统上下文；代码评审阅读完整送审差异，按影响追踪调用方、规则拥有者、数据与错误路径。作者说明用于理解意图，实际行为需与代码核对。大型变更先建立行为与文件的映射；无法可靠覆盖时，明确未审部分，不能将抽样结论写成完整审查。

## 选择评审层级

按完整名称找到并读取需要的专项，复用已加载内容。专项按自身清单评审，不启动实现或其他评审流程。

| 层级 | Skill | 关注与使用条件 |
| --- | --- | --- |
| System design | ao-sdlc-system-design-review | 系统整体职责、契约、数据与运行方式；用于设计稿或影响系统边界的改动 |
| Code change scope | ao-sdlc-change-scope-review | 本次 diff 的目的、完整性、logical bundles 与拆分；明确单个 commit 或完整送审范围 |
| Implementation-level：functionality | ao-sdlc-functionality-review | 实现是否满足需求；检查正常、边界、失败行为与验证证据 |
| Implementation-level：code quality | ao-sdlc-code-quality-review | 实现是否合理易维护；检查结构、naming、repo integration、惯例适用性与 smells |

通常按表中顺序组织完整 review；按用户指定对象和实际风险选择层级，不将每层变成固定关卡。已有代码的完整评审通常包含 scope、functionality 与 code quality；局部常量修正只需相称检查，不重审整个系统。仅有设计稿时评审方案与验证计划，不要求尚不存在的代码或测试结果。用户只要求某层时限定该层及必要上下文。

Implementation-level 是两个专项的逻辑分组，不再增加转发入口。Functionality 主要回答行为是否正确，code quality 主要回答结构与维护成本是否合理；同一问题允许跨层发现，以具体后果和证据归并，不强行互斥。同一根因只报告一次，并保留有关层级的依据。

专项不可用时，说明缺失与覆盖限制，完成可做部分，不声称已执行该专项。检查采用已核实、有问题、待确认或不适用四种状态；未检查不能记为通过。最终输出重点发现和关键缺口，用户要求完整 checklist 时再展示逐项状态。

## 共用 Checklist

- [ ] **目标与版本**：目标、基线、送审快照和项目要求是否明确？证据是否对应本次快照？
- [ ] **覆盖范围**：是否覆盖实际改动风险、必要调用方与配套？是否明确未审范围？
- [ ] **判断依据**：结论来自需求、契约、项目约束还是具体维护成本？是否仅凭风格偏好或模式名称提出问题？
- [ ] **发现归属**：问题是本次引入、加重，还是既有且未受影响？是否确实阻碍当前目标？
- [ ] **因果与反证**：触发条件、位置和后果能否连起来？是否核对调用约束、已有保护和作者解释？
- [ ] **验证质量**：证据是否验证预期行为与关键失败路径？声称保持行为时是否界定边界，声称性能收益时是否使用可比较的负载与指标？
- [ ] **优先级与去重**：是否按影响和确定性排序？同一根因是否合并？修正方向是否引入无关范围？
- [ ] **结论边界**：是否区分阻塞问题、非阻塞建议、待确认项和重要未验证范围？是否将静态阅读、mock 或未运行检查误写成实际验证？

## 核实与交付

每个实质发现包含位置、触发条件、具体后果、证据及必要时的最小修正方向。沿用项目严重度标准；没有约定时区分阻塞问题、非阻塞建议和待确认项，并解释阻塞理由。关键契约无法核实时可构成推进条件，但必须明确为决策或证据缺口。

报告先给出发现，再说明整体结论、版本、已审范围、实际执行的检查与限制。不要求固定数量的 findings。没有实质问题时可写明“在已审范围内未发现阻塞问题”；关键待确认项尚未解决时，说明暂不能作出的判断。

修正复核检查新快照、原问题及受影响部分。新证据推翻旧意见时关闭意见；修改扩大影响面时再增加检查。已通过且未受影响的部分无需全量重跑。

审查产出意见。修改代码、拆分提交、发布评论或合并按用户已有授权执行；没有相应授权时保持只读。

## 判断边界

- 基线已有的日志格式问题与本次解析修复无关：不据此阻塞修复；若要记录，标为既有问题。
- 多个维度都发现连接失败被转换为空结果并引起数据删除：合并同一根因，保留完整因果链。
- 有效输入约束推翻原意见：关闭意见，不为保留 finding 更换理由。
