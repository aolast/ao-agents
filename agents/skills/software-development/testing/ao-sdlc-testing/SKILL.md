# 测试与验证

围绕当前要作出的决定取得证据：一个函数能否继续集成、一个 module 的契约是否成立，或一个 feature 是否达到交付要求。验证可以是自动化测试、静态检查、人工操作或运行环境观测；每种证据只支持其实际覆盖的结论。

运行会写入文件的验证前，确认项目已安排或本任务隔离的工作区与测试环境；缺少明确安排时先补齐，不能把可访问的共享目录或服务视为已获准使用。已有明确安排时复用。仅审阅测试设计或证据时，不启动工作区准备或分支操作。

## 在当前阶段确定验证范围

先读取项目的测试入口、验收要求与必需关卡，复用仍适用的验证计划和结果。用几句话明确本轮的对象与版本、要证明的判断、必要场景和证据、完成条件及留到后续阶段的事项；小任务无需独立测试计划。项目没有明确要求时，根据契约、影响面与失败后果作出有依据的选择，不等待一份不存在的统一标准。

- **需求与设计阶段**：确定 feature 的可观察验收结果、关键失败行为及验证所需环境；把需要局部、跨边界或端到端证据的判断分清。此时的产出是可执行的验证计划，尚不存在的实现不要求先交出测试结果。
- **增量实现阶段**：按正在改变的契约选择检查，及时发现局部错误和受影响的交互。局部验证完成后可以继续实现或集成，后续 feature 验收仍需补齐；一个增量不必反复运行整个产品的全部测试。
- **集成与交付阶段**：核对完整 feature 的验收证据、实际接线和项目对当前交付阶段的关卡。合入代码、发布及上线验证各有要求，不能相互代替。

阶段与测试层级不是固定对应关系：实现中也可能需要端到端实验，feature 验收也会复用局部测试。按待证明的判断选择最小且可信的验证边界：

| 对象与判断 | 主要证据与本轮完成边界 |
| --- | --- |
| Function 的计算或转换契约 | 覆盖相关输入、输出、边界和错误；必要场景通过且调用假设有依据后，可结束该局部验证 |
| Class / module 的职责、状态及接口契约 | 核对公开行为、状态转换、生命周期及受影响消费者；有真实依赖协议或存储语义时补相应集成证据，不能仅凭类内单测推断边界成立 |
| Feature 的用户可见结果与跨组件链路 | 核对从实际入口到结果的必要链路及关键失败场景；端到端检查聚焦接线和协作，细粒度输入组合由更局部的测试覆盖 |

这些是选取证据的依据，不是固定测试数量或项目通用的放行标准。改动行数少也可能影响关键链路；所处层级高也不要求穷举所有内部状态。

## 选择与实施验证

1. 从需求或设计中的契约推导预期结果。覆盖本次相关的正常行为、关键边界、失败与恢复路径；重试、取消、并发、兼容性等场景按实际影响选择。
2. 优先采用能暴露真实缺陷、范围最小且可靠的检查。Mock 放在明确的外部边界，不替换要验证的关键逻辑；模拟成功不能代替真实集成成功。
3. Bug 修复有条件时让回归用例在基线失败、修改后通过。无法重现时说明限制，不把新用例通过当作根因已证实。
4. 断言可观察契约，避免复制实现计算预期值或绑定无关私有细节。控制相关的时钟、随机性、外部状态与数据；重跑偶然变绿不能证明不稳定问题已修复。
5. 复用现有 fixture 和测试组织方式。低风险文档修改可以通过阅读和既有检查验证；覆盖率辅助定位空白，不替代风险判断，也不为数量编写无意义测试。

## 何时调整或停止

在本轮开始时确定完成条件；出现新行为、影响面变化、失败或证据失效时，只调整相关部分。调整应能回答“哪项判断尚缺证据，新检查如何补足”，并更新本轮范围；不因还能想到更多场景就持续扩大。

| 当前情况 | 行动与结论 |
| --- | --- |
| 本轮必要判断已有对应版本的可信证据，适用的必需关卡满足，且没有否定当前结论的已知问题 | 结束本轮验证，说明可支持的结论和限制；没有新证据或变更时，不为增加信心反复跑同样检查 |
| 必要检查失败、缺失或结果不足以支撑判断 | 针对具体缺口修复、补查或调整方案，再复核受影响部分；不能用大量无关通过结果抵消缺口 |
| 环境、权限或外部依赖阻止取得必要证据，继续重复不会增加信息 | 停止无效尝试，交付阻塞原因、已有证据和恢复验证的条件；验证未完成，不宣称通过 |

风险不必全部消失才能结束一轮验证。区分影响当前验收的缺口、后续阶段的必要检查，以及不阻碍当前结论的残余风险。后两者记录适用边界和后续处理；需要豁免项目关卡或改变验收标准时，沿用项目的决策权限，已有有效决定不重复征求。不能为了结束测试，把本轮未满足的要求自行挪到以后或声称风险已被接受。

时间或成本受限时，可结束执行并交付未完成状态，不能据此降低通过标准。产品缺陷、环境／fixture 问题与既有基线失败分别说明；部署观测缺失时，不声称已上线有效。

## 结论 Checklist

- [ ] **范围**：当前阶段、验证对象和要支持的结论是否明确？局部通过是否被错误扩大为 feature 或上线通过？
- [ ] **证据**：必要场景与项目关卡是否有对应版本的结果？Mock、静态阅读及实际运行的边界是否清楚？
- [ ] **停止或补查**：本轮完成条件是否满足？继续检查是否针对具体缺口，还是重复已有证据？
- [ ] **限制**：未覆盖项属于当前阻塞、后续检查还是残余风险？是否存在未经授权放宽验收的情况？

结果用简短的“验证对象／方法与命令／结果／结论与缺口”记录，包含对应版本和关键环境。复杂结果才用表格。

## 边界示例

- 修复金额转换函数，项目要求的精度、舍入与错误场景均通过，调用方契约未变且已核对：结束局部验证，无需自行扩展成全站购买流程测试。若项目要求合入前跑完整套件，该关卡仍适用。
- 订单导出 module 的权限与序列化测试通过，但 feature 要求用户能从界面下载，路由尚未接线：module 验证可以结束，feature 验收不能据此通过。
- 项目要求交付前在 staging 验证上传链路，但 staging 不可用：交付验证缺口及恢复条件，停止重复连接；不能改称“单测已通过，所以验收完成”。
- 上传超时变更已满足本轮约定场景，移动网络切换经影响分析不影响本轮结论，且不属于适用关卡：记录未覆盖范围后停止。若项目明确要求覆盖网络切换，则它仍是必要证据，不能套用此前项目的停止条件。
