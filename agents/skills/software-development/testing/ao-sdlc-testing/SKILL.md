# 测试与验证

从目标项目的测试入口、预期行为和本次风险出发。验证可以是自动化测试、静态检查、人工操作或运行环境观测；说明每种证据能支持的结论。

## 选择验证

1. 对照需求或 [design](../../design/ao-sdlc-design/SKILL.md) 中的契约列出需要证明的判断，不从改了哪些行直接推导全部测试。
2. 优先采用能暴露真实缺陷、范围最小且可靠的检查。业务逻辑可局部验证，跨边界契约需要相应集成证据；只在必要链路上运行端到端验证。
3. 覆盖本次相关的正常行为、关键边界、失败与恢复路径。重试、取消、并发、兼容性等场景只在变更影响到它们时增加。
4. Bug 修复有条件时让回归用例在基线失败、修改后通过，以确认它捕获的是原问题。无法重现时如实说明，避免把新用例通过当作根因已证实。

## 测试质量

- 断言从需求或契约得到的可观察结果；避免复制实现计算预期值，或仅断言内部调用次数而无法发现错误行为。
- Mock 使用在明确的外部边界，不把要验证的关键逻辑替换掉。区分模拟成功与真实集成成功。
- 控制与场景相关的时钟、随机性、外部状态和测试数据。重跑偶然变绿不能证明不稳定问题已修复。
- 复用现有 fixture 和测试组织方式。小幅文档或低风险可逆修改可以通过阅读和既有检查验证，不强制新增单测。
- 覆盖率可辅助定位空白，不替代风险判断；不写只锁定措辞、标题或偶然实现细节的测试。

## 执行与结论

标明被测代码版本或工作区状态、命令、关键环境、结果和未覆盖范围。修改后旧证据是否仍适用，按实际受影响部分判断。

区分产品缺陷、环境／fixture 问题和既有基线失败；必要时调用 [investigation](../../investigation/ao-sdlc-investigation/SKILL.md) 定位，不能用忽略失败或放宽断言取得通过。

当已有证据足以支持当前任务且没有未解决风险或必需关卡时，停止扩大测试。部署环境验证缺失时，把限制交付给决策者，不声称已上线有效。

结果用简短的“验证对象／方法／结果／缺口”记录；复杂结果才用表格。审查测试时引用这些标准，不另造一套完成条件。

## 边界示例

- 重试单测 mock 了整个重试函数，只验证返回成功：不能据此证明重试边界或副作用正确。
- 修改纯说明文字：核实内容与链接即可，不为了满足测试数量增加文本快照用例。
