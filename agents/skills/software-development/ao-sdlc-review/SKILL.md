# 软件审查

先确认原始目标、项目约定和审查对象：设计稿、PR/CR、commit 或未提交变更。代码审查明确基线和实际 head；未提交改动单独标明。作者说明是意图和线索，实际行为需通过代码与证据核实。

## 建立审查视图

阅读完整变更，并按影响追踪调用方、规则拥有者、数据与错误路径。不能只读描述，也不必无目的地扫描整个仓库。

按本次涉及内容选择并读取标准；已加载部分直接复用：

| 判断内容 | 标准维护源 |
| --- | --- |
| 目标、scope、方案、契约、交付拆分 | [design](../ao-sdlc-design/SKILL.md) |
| 实现结构、依赖、错误和资源处理 | [implementation](../ao-sdlc-implementation/SKILL.md) |
| 测试质量、验证证据与缺口 | [testing](../ao-sdlc-testing/SKILL.md) |
| 重构所需的行为保持边界 | [refactoring](../ao-sdlc-refactoring/SKILL.md) |
| 性能收益及测量可比性 | [performance-optimization](../ao-sdlc-performance-optimization/SKILL.md) |

引用时执行当前审查所需的判断，不反向启动实现或另一轮完整审查。仅设计稿的审查不要求已有代码和测试结果，可以要求可执行的验证方案。

## 核实问题

- 给每个问题找到触发条件、位置、依据和具体后果；无法建立因果链时继续调查或明确提出问题，不将猜测写成确定缺陷。
- 区分本次引入的问题、既有问题和本次使之恶化的问题。既有问题只有确实阻碍当前变更时才成为本次阻塞项。
- 阅读反例、测试和作者解释。审查必须允许“原意见不成立”这一结论，不为维持结论继续寻找替代理由。
- 同一根因的问题合并表达，优先交付影响大且确定性高的发现。建议保持与风险相称，不将个人风格偏好包装为正确性缺陷。

## 交付与复核

使用 [communication](../ao-sdlc-communication/SKILL.md) 撰写意见。每个实质问题简要包含：位置或版本、条件、后果、证据，以及必要时的修正方向。标明阻塞问题、非阻塞建议和待确认信息；有项目严重度标准时沿用，不自建复杂分级。

没有实质问题时明确说明未发现阻塞项，并列出重要的未验证范围；不要求固定数量的 findings。整体结论与事实一致，不将“未发现问题”写成对所有环境的保证。

修正后核对新快照及受影响部分；新证据推翻旧意见时关闭旧意见。已通过且未受影响的部分无需反复全量检查。审查授权不自动包含改代码、发布评论或合并；已有明确授权按任务执行。

## 边界示例

- 基线已有的日志格式问题与本次解析修复无关：可单独提及，但不据此阻塞当前修复。
- 新路径在连接失败时将错误转成空结果：说明触发条件和调用方误判的后果，再提出修正方向。
