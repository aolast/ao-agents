# 软件设计

基于目标项目规则和相关实现，明确需要改变的行为及必须保持的约束。已由用户确定的选择作为输入，不重新替换目标。

## 问题与 scope

1. 用可观察结果表述目标，区分现象、需求和预先选定的解决办法。原因为何尚不清楚时，按需使用 [investigation](../../investigation/ao-sdlc-investigation/SKILL.md)。
2. 明确这次的目标、非目标、验收条件与不变量。只追问会改变方案的重要未知项；低影响、可逆的细节可作出合理假设并继续。
3. 找到规则的拥有者、相关调用者和数据流，确定修改边界，避免在多个入口重复维护同一业务规则。
4. 检查是否遗漏必要的调用方、配置、迁移和文档，也检查是否夹带无关整理。

技术债按实际影响判断：阻碍当前任务或正由本次变更继续扩散的部分，考虑一并处理；独立问题记录其影响与后续建议；局部整理只在能降低本次复杂度且验证成本可控时纳入。不要把“顺便清理”扩大成无边界重写。

## 方案与契约

- 记录足以指导实现的输入、输出、失败语义和责任归属。涉及持久化、并发或跨进程交互时，再明确顺序、幂等性、一致性及资源约束。
- 对确有取舍的选项比较正确性、复杂度、运维代价和可逆性；没有实质竞争方案时，不为凑选项制造替代设计。
- 若契约变化，标明受影响的消费者和兼容策略。迁移期间的新旧行为、发布顺序及恢复方法按实际风险说明。
- 用 [testing](../../testing/ao-sdlc-testing/SKILL.md) 确定怎样取得验收证据；实现细节遵循 [implementation](../../implementation/ao-sdlc-implementation/SKILL.md) 的质量标准。

## 拆分与交付

按可理解、可验证的目标拆分交付，不按文件数或代码行数机械切分。说明单元间依赖、中间状态是否可用，以及必要迁移是否可以独立发布。

区分 code change 与评审请求；一个 PR/CR 可以包含紧密相关的多个 code changes。提交数量与合并方式遵循目标仓库，不在此规定统一 Git 策略。

产出可短至几句话，复杂任务才需要设计文档。保留：目标与范围、采用方案及关键理由、影响的契约、验证办法、会改变决策的未知项。用 [communication](../../communication/ao-sdlc-communication/SKILL.md) 组织给读者的说明。

## 边界示例

- 增加重试会影响幂等性和调用成本：应明确哪些失败可重试及重复执行的结果，不能只写“提高稳定性”。
- 修正一个含义明确的常量：说明依据与验证即可，不要求完整方案比较、迁移设计或正式设计评审。
