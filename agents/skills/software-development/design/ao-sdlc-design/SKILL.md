# 软件设计

基于目标项目规则和相关实现，明确需要改变的行为及必须保持的约束。已由用户确定的目标和约束作为输入；发现与现实条件冲突时，指出证据及影响，只重新讨论受影响的决定。

## 设计深度与实现边界

设计确定需要共同遵守的行为、契约和关键取舍；具体代码组织通常在实现时细化。边界由决定的影响与修改代价划分，不按是否提到 class、function 或 module 划分。

需要协同实现的接口、状态与资源归属、信任边界、并发模型以及难以局部撤销的选择，应在依赖它们的实现展开前明确。私有函数拆分、局部命名及等价控制流，可留给实现者结合代码决定。Low-level design 在能消除关键不确定性或协调多个实现方时有用，不要求提前列出所有 class 和 function。

交付方案时区分必须满足的约束、已有依据的设计决定、示意结构及仍需验证的假设。对要求固定的低层结构说明理由，让实现者知道哪些可以调整。已有设计足以指导工作时直接使用；实现中的事实推翻某项假设时，只修订相关决定和受影响的契约、验证计划，不从头重做整个设计。

## 问题与 scope

1. 用可观察结果表述目标，区分现象、需求和预先选定的解决办法。原因为何尚不清楚时，明确需要调查的问题与证据，不将未验证的解释作为方案前提。
2. 明确这次的目标、非目标、验收条件与不变量。只追问会改变方案的重要未知项；低影响、可逆的细节可作出合理假设并继续。
3. 找到规则的拥有者、相关调用者和数据流，确定修改边界，避免在多个入口重复维护同一业务规则。
4. 检查是否遗漏必要的调用方、配置、迁移和文档，也检查是否夹带无关整理。

技术债按实际影响判断：阻碍当前任务或正由本次变更继续扩散的部分，考虑一并处理；独立问题记录其影响与后续建议；局部整理只在能降低本次复杂度且验证成本可控时纳入。不要把“顺便清理”扩大成无边界重写。

## 方案与契约

- 记录足以指导实现的输入、输出、失败语义和责任归属。涉及持久化、并发或跨进程交互时，再明确顺序、幂等性、一致性及资源约束。
- 对确有取舍的选项比较正确性、复杂度、运维代价和可逆性；没有实质竞争方案时，不为凑选项制造替代设计。
- 若契约变化，标明受影响的消费者和兼容策略。迁移期间的新旧行为、发布顺序及恢复方法按实际风险说明。
- 明确当前设计阶段需要消除的关键未知项、实现阶段的局部验证与 feature 验收所需证据，以及适用的项目关卡；将验证留在合适阶段，不把测试计划当作执行结果。

## 拆分与交付

按可理解、可验证的目标拆分交付，不按文件数或代码行数机械切分。说明单元间依赖、中间状态是否可用，以及必要迁移是否可以独立发布。

区分 code change 与评审请求；一个 PR/CR 可以包含紧密相关的多个 code changes。提交数量与合并方式遵循目标仓库，不在此规定统一 Git 策略。

产出可短至几句话，复杂任务才需要设计文档。保留：目标与范围、采用方案及关键理由、影响的契约、验证办法、会改变决策的未知项。

## 边界示例

- 增加重试会影响幂等性和调用成本：应明确哪些失败可重试及重复执行的结果，不能只写“提高稳定性”。
- 修正一个含义明确的常量：说明依据与验证即可，不要求完整方案比较、迁移设计或正式设计评审。
- 草图用三个 class 表达解析步骤，未要求独立状态或扩展接口：实现可按仓库结构采用少量纯函数；若三个对象分别拥有连接、事务和后台任务生命周期，则应先保留这些责任，不能只按数量合并。
- 方案假设上游支持幂等请求，但实际接口没有去重保证：重新讨论重试与副作用，不继续按原图实现；其他未受影响的方案无需重开。
