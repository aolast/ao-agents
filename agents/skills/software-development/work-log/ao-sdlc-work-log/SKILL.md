# 工作记录与恢复

让接手者迅速知道目标、实际状态、可信证据和下一步。允许丢失能够廉价重建的次要细节，以明显低于返工的成本维持连续性。

## 何时记录

- 交接、暂停或切换任务之前，更新当前 checkpoint。
- 获得重新调查成本较高的结论，或方案、约束、阻塞明显变化时，及时记录。
- 长任务中未记录的成果已多到丢失会显著返工时，补一个 checkpoint；不要完全依赖结束前才保存。
- 短小任务若已有清楚的变更和交付说明，可以不单建日志。不逐工具调用写流水账，不强制固定时间间隔。

## 最小记录

沿用项目已有任务记录位置；没有约定时，在当前任务使用的 issue、文档或可持久化工作记录中选一处，避免并行维护多个副本。写入外部位置须处于当前任务授权范围；不要将记录自动塞入全局 AGENTS.md。

用简短段落或下列字段组织，省略没有内容的项：

- **目标与约束**：接手者要达到什么结果，哪些决定仍然有效。
- **工作位置与状态**：仓库、分支／commit、关键文件、未提交或仅本地存在的修改；区分已完成、进行中和计划。
- **关键发现／决定**：有来源的事实、尚待验证的假设、重要选择及理由；只保留有助于避免高成本重复尝试的失败路线。
- **验证**：已执行的方法、对应版本或工作区状态、结果与缺口；细节可链接到测试或 CI。
- **阻塞与下一步**：一个明确可执行的起点，说明还需什么证据或决定。

记录更新时间。优先更新一份当前状态摘要，仅为必要的决定保留简短历史。引用已有设计、代码和工单，不复制全文；不存凭据或无关私密数据。

## 恢复工作

1. 读取目标项目入口和最新 checkpoint，核对真实分支、commit、工作区与关联 PR 状态。
2. 识别记录之后发生的变化；对版本敏感或失去来源的结论重新验证，不从头重跑所有已确认工作。
3. 从下一步继续；若记录与事实冲突，先修正当前状态和受影响判断。记录只是恢复线索，不能替代代码、授权或验证事实。

工作日志不是代码备份。若下一步依赖仅本地存在的代码，交接时须提供适当的可访问修改、补丁或明确说明尚不可恢复，不能只写“实现完成”。记录未提交内容不等于获得提交／推送授权。

## 边界示例

- 正确记录：“分支上的修复已保存；回归测试针对上一个 commit 通过；随后修改的取消路径尚未测。下一步运行取消场景。”接手者不会误认为最新代码已验证。
- 修改一个拼写后立即交付，且没有调查结论需要保留：无需创建独立 work log。
