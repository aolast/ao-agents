# 如何写 Commit Message

基于本次提交实际包含的 code change 和已有证据写作。让读者能从 title 辨认这次变化，从正文理解变化的原因、影响和必要取舍。正文只补充有用的信息；简单变更可以只有 title。

## 写作前：确认范围与项目约定

先阅读本次提交对应的 diff 和必要上下文，明确哪些变化属于本次提交。审查已有 message 时同样对照实际变化；不要把整个任务、整个 review request 或其他提交的成果算进来。动机、验证结果等无法从 diff 确认的信息，依据已有记录或向用户补充了解，不编造。

格式、语言与篇幅按以下顺序确定；上一级只规定部分事项时，其余事项继续向下判断：

1. **项目明文规定**：检查适用的 `AGENTS.md`、`CONTRIBUTING.md`、开发规范及实际生效的提交校验配置。明确规定优先于历史中的不同写法。
2. **项目隐含惯例**：没有相应明文规定时，确认项目实际主分支及最新状态，查看其最近至少 **10 个 commit 的完整 message**，包括 title 和正文。不要用当前任务分支的临时提交或只含标题的列表代替。历史总数不足 10 个时查看全部，说明样本有限；浅克隆或无法访问历史不等于项目没有历史。
3. **本 skill 默认规则**：没有稳定惯例时，使用下文的 Conventional Commits 简明指南。无法核实历史时说明限制，按默认规则起草，不声称已经确认项目没有惯例。

从历史判断语言、title 结构、正文篇幅及附加字段的稳定用法。区分人工提交和自动生成的 merge message、机器人提交；必要时向前扩看，不让自动文本主导判断。混杂且无法识别稳定做法时，视为该事项没有惯例。历史中的空泛描述和遗漏理由不构成内容质量标准。

Conventional Commits 不决定正文语言。项目没有语言约定时沿用用户任务中的语言，保留必要英文术语；无需向 message 加入格式选择过程。

## Title：写出能辨认的具体变化

Title 应独立说明这次提交做了什么。读者只看提交列表，也应能判断它是否与自己有关，并将它与相似提交区分开。

- 优先写具体结果或行为变化；按需要加入对象、触发条件或影响范围。描述真实变化，避免“优化”“完善”“修复问题”等无法辨认的概括。
- 实现动作只有在它本身就是重点，或能帮助辨认变化时才进入 title。例如重构可以写内部结构的改变，不必虚构用户可见收益。
- 根据本次提交的实际贡献写 title，不直接照抄 issue 标题；issue 编号和 type 也不能代替有信息的描述。
- 选择最能概括本次目的的一句话；动机、机制和次要变化放到正文。项目未规定时保持单行简短，不为凑字符数删掉关键条件。

例如：

| 不够具体 | 更有用的 title |
| --- | --- |
| 修复订单问题 | 防止订单请求重试时重复创建订单 |
| 给订单接口增加唯一约束 | 防止并发重试创建重复订单 |
| 优化解析器 | 将重复的日期解析逻辑集中到一个函数 |
| 更新文档 | 说明超时重试应复用原请求标识 |

## 正文：选择展开程度

以下提供完整正文和精简正文两套写法，区别在于成稿展开多少。完整写法也只保留必要信息；项目要求简短，或少量文字已经足够说明变化时，采用精简写法。不要固定填满 `What / Why / How / Testing` 栏目。

### 完整正文写法（长版本）

先补足 title 未容纳的变化及影响，再说明原因、关键机制和取舍。一般用几个紧凑段落即可；只有内容确实较多时才使用小标题或列表。

围绕本次变化选择需要回答的问题，不逐项填空：

- **变化与动机**：什么条件下，变更前的行为有什么问题或限制？本次提交改变什么，为什么值得改？重构说明改善的具体维护负担，以及预期保持的行为。
- **关键机制与取舍**：解释实现怎样产生上述效果，尤其是 diff 中不明显的联系。看似更简单的方案为何不可行、新依赖为何必要、为何只处理部分情形，都在确实影响理解时交代。
- **影响与边界**：说明已知副作用、不兼容变化和迁移方式。若本次只是更大计划的一步，只说明理解当前选择所需的关系，清楚区分已完成内容与后续意图。
- **证据与限制**：保留能帮助判断的实验结果、特殊复现或测试方法，以及重要的未验证情形。常规检查通过不必逐条报账；不能把预期效果、本地测试和线上运行事实混为一谈。
- **可追溯上下文**：对相关 issue、历史 commit、标准或调查结论，先摘要说明与本次变化有关的事实，再附必要引用。独特报错或组件名称有助于后续搜索时保留；不要只给链接让读者重新调查。

明确写出哪些行为属于变更前，哪些属于应用本次提交后，不只靠时态或孤立的“现在”。描述关键机制是为了帮助理解变化，无需逐行解说代码。

### 精简正文写法（短版本）

目标是把 commit message 本身写短，同时让读者理解核心变化和关键理由。可直接起草一小段，也可将完整草稿压缩；不要求先写一篇长文。

1. **让 title 承担变化摘要。** 正文不要再次完整复述 title；补充缺少的触发条件、原因或取舍。通常一小段、一至三句就够，项目有具体长度要求时按其要求。
2. **保留最关键的因果关系。** 优先说明“在什么情况下有什么问题，为什么这样处理”。机制只保留能解释效果或关键取舍的部分，不展开类名、文件路径和调用过程。
3. **按信息价值删减。** 先删重复和空话，再删开发过程、常规验证报账、易从 diff 看出的动作；最后压缩一般背景和次要方案讨论。用准确的对象和动词缩短句子，不靠含糊缩写或堆术语。
4. **保留会改变判断的事实。** 不兼容影响、必要迁移、已知重要副作用、关键验证限制不能为了短而消失。将它们压成直接的句子，优先于一般背景保留。
5. **最后判断正文是否还有增量信息。** 若 title 已经充分说明简单变更，且没有需要补充的理由或影响，可以省略正文。不要为了有正文而重复标题，也不要把尚有必要解释的变更压成“见 issue”。

项目若只允许 title，优先在 title 中表达核心变化及重要影响；无法容纳的必要说明按项目规定的位置保存，并向用户指出这一限制，不静默丢弃。

### 同一个变化的两种写法

以下是虚构示例，展示成稿的展开程度；实际写作只能采用本次变化已有的事实与证据。

完整正文：

```text
fix: 防止并发重试创建重复订单

变更前，创建订单接口先检查请求标识，再插入订单。并发重试可能同时
通过检查，为同一次下单创建多个订单。

本次提交使用数据库唯一约束保证同一请求标识只创建一个订单；
发生冲突时返回已有订单。客户端需要在重试时复用原请求标识。

只在应用进程内加锁无法覆盖多个服务实例，因此由数据库保证唯一性。
新增的并发回归测试已通过；尚未验证跨地域部署下的重试行为。
```

精简正文：

```text
fix: 防止并发重试创建重复订单

先检查再插入无法阻止并发重复写入，改由数据库唯一约束去重并返回
已有订单；客户端重试须复用原请求标识。并发回归测试已通过，
跨地域部署尚未验证。
```

精简版保留了问题原因、关键机制、调用方要求和验证限制，省去了过程展开与替代方案讨论。简单变更则可以只有 `docs: 修正文档中 request_id 的拼写`。

## 哪些内容应省略或放到别处

- **Diff 的机械复述**：文件清单、逐行修改和可直接看出的 API 调用通常不写。确实能引导读者找到关键变化的位置或解释机制时，才保留相关细节。
- **长期维护说明**：接口契约、使用方法和维护不变量放在代码、测试或项目文档中；message 可以摘要说明它们如何变化及为何变化，不能成为唯一维护依据。
- **临时协作信息**：评审喊话、催办、交接状态、临时预览地址和短期构建产物链接放在讨论或工作记录中。
- **过程噪音**：不保留完整执行日志、浏览历史、反复尝试的流水账和无关故事。只留下能避免重复调查或解释取舍的结论。
- **缺少依据的断言**：不虚构测试结果、收益数字、迁移方案或关联编号；不能把计划写成完成。还未确认且影响准确性的事实应补证或明确限制。

## Conventional Commits 简明指南

以下是项目没有明确规则或稳定惯例时的默认规范，在本 skill 内维护即可完成写作，无需访问外部文档。它采用 Conventional Commits 1.0.0 的基本语法，并收紧可选字段的使用。

### 默认结构

普通提交使用 `<type>: <description>`。存在正文时，与 title 空一行；正文用普通段落，需要时使用简单列表。保证在纯文本中可读，长段落适当换行，不依赖 Markdown 渲染。没有项目要求时，不把 50/72 等字符数作为硬性门槛。

`description` 按上文的 title 方法撰写；type 使用下表的小写英文词，描述与正文采用已确定的语言。

| Type | 使用情形 |
| --- | --- |
| `feat` | 增加功能或能力 |
| `fix` | 修复错误行为 |
| `docs` | 只修改文档或说明 |
| `refactor` | 调整内部结构，预期保持外部行为 |
| `perf` | 以性能改善为主要目的 |
| `test` | 只增加或修改测试 |
| `build` | 构建系统、打包或依赖变更 |
| `ci` | CI 配置与流程变更 |
| `style` | 不影响含义的代码格式调整；不是界面视觉功能变更 |
| `chore` | 不属于以上类型的日常维护 |

按提交的主要目的选择一个 type。例如修复 bug 同时增加回归测试仍用 `fix`；不要因为某个文件类型或附带动作改变分类，也不要把 `chore` 当作无法概括目的的兜底词。这张表是本 skill 的默认词表，并非上游规范要求的完整枚举。

### Scope、footers 与 tags

默认不写 scope、footers 或方括号标签等附加 tags。只有项目明文规则或稳定历史使相应字段的含义和用法清楚时才采用；看到零星使用不等于已有共识，不自行发明分类或标签系统。

- **Scope**：项目明确使用时写作 `<type>(<scope>): <description>`，scope 沿用项目定义。没有明确 scope 时，把必要的影响范围自然写进 description。
- **Footers**：项目有要求时，按其定义在正文后空一行追加，例如 `Signed-off-by: ...`。常见结构为 `Token: value` 或 `Token #value`，普通 token 的多个单词用连字符连接；特殊的 `BREAKING CHANGE` 保留空格。签署、归属和编号必须有依据，不自动添加署名或工具归属。
- **Tags 与关联编号**：只有项目有明确用法时才添加额外标签或标题中的编号前缀。没有相应约定时，必要的 issue 或 commit 关联可以放进正文的解释句，无需另造 `Refs:` 等 footer；不要擅用带自动关闭含义的关联词。

### 不兼容变更

没有项目 footer 约定时，使用 `<type>!: <description>`，并在 description 或正文说明不兼容影响与迁移方式。若使用 scope，`!` 放在右括号之后。任何 type 都可能包含不兼容变更，不只限于 `feat`。

例如：

```text
feat!: 将订单查询参数从 orderId 改为 order_id

请求参数 orderId 不再被接受，调用方须改用 order_id。
```

项目规定使用 footer 时，采用 `BREAKING CHANGE: <影响与迁移说明>`；项目要求同时使用 `!` 时也须满足。不能因为默认省略 footers 而漏报不兼容变化。Conventional Commits 只提供表达约定；选择 type 或标记不代表已经执行版本发布。

## 完成前核对

对照实际 diff 检查 title 和正文是否准确，删除重复和无助于理解的细节，确认没有遗漏重要影响、混淆前后行为或夸大验证结果。审查任务指出具体问题并给出改写；撰写任务交付可直接使用的 message，必要的假设或信息缺口放在 message 之外说明。

本 skill 只负责写作与审查，不执行 commit、改写历史或创建 review request。

内容方法主要参考 [Michael Lynch：How to Write Useful Commit Messages](https://refactoringenglish.com/excerpts/commit-messages/) 和 [Simon Tatham：Writing commit messages](https://www.chiark.greenend.org.uk/~sgtatham/quasiblog/commit-messages/)；基本格式核对 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)（阅读与核实于 2026-09-08）。
