# 如何写 Review Request

让 reviewer 不依赖作者的会话历史，也能理解本次送审的目的、范围和需要判断的事项。正文的展开程度取决于理解变更所需的信息；简单变更可以用一两句话加必要的验证说明。

Review request 是送审请求，可以包含一到多个紧密相关的 code changes。在具体平台使用实际称呼，如 GitHub PR、GitLab MR；描述实现内容时使用 code change 或“变更”，不把请求本身当作代码。

## 与 Commit Message 的互补关系

Commit message 更偏向单次提交的细节，review request 更偏向整次送审的 context。两者从不同层次解释同一项工作：

- **Commit message**：说明这次提交具体改变了什么、为什么这样实现，以及理解这些细节所需的约束和取舍。它帮助后续读代码或追溯历史的人理解该提交，不是逐行复述 diff。
- **Review request**：说明为什么要做这项工作、它处于什么背景下、整体目标和范围是什么，以及各项 code changes 如何共同完成目标。它帮助 reviewer 建立整体理解，再判断方案、影响和验证是否充分。

写 review request 时，先补足 reviewer 尚不知道的 context，再选择会影响整体判断的实现细节。例如，commit message 可以解释唯一约束如何处理并发冲突；review request 则需要说明为什么订单重试需要幂等保证、客户端与数据库的改动如何配合，以及历史数据如何影响交付。

这是侧重点的区别，不是把“为什么”只留给一方，也不是要求两份文字完全不同。理解整次送审所必需的细节可以在正文中摘要，不能只写“见 commit message”；也不应把各个 commit 的细节原样堆成正文。只有一个 commit 时，两者可以有较多重合，仍按各自读者需要选择信息。

## Format：项目要求优先，形式与内涵分别核对

对应项目的明确要求优先于个人偏好，包括本 skill 的默认写法。先采用项目指定的语言、标题格式、栏目、顺序和必要字段；未规定的部分再按个人偏好组织。不默认要求 Conventional Commits，也不将某个平台的格式推广到所有项目。

项目模板通常规定信息放在哪里、以什么形式呈现；写作还要判断这些信息是否真正回答了问题。符合格式不等于解释到位。项目若明确要求实质内容，也同样遵守；不能把项目要求一概视为只有形式。

例如，同样填写“动机”栏目：

- “增加请求标识和唯一约束”只重复了 code change 的内容，没有说明目的。
- “客户端超时重试可能创建重复订单；需要保证一次下单无论重试多少次都只产生一个订单”说明了问题和希望达到的结果。

将有用的 context、理由和限制写进项目对应栏目，不为坚持个人结构另起一套重复正文。没有专门的“未完成事项”栏目时，放在范围、风险或其他合适位置；格式简短也不能成为隐去重要事实的理由。

## 写作前：确认送审内容

- 核对目标分支、送审版本及完整 diff，结合必要的实现、设计和任务背景确定实际范围。不能只看最后一个 commit，或直接拼接开发期间的 commit messages。
- 区分本次已实现的内容、后续计划和未解决问题。已有 issue 或设计文档可以引用，但先摘要说明与本次变更有关的背景，不让 reviewer 必须追溯整段历史。
- 材料不足时，先起草有依据的部分，明确影响判断的缺口；不编造动机、验证结果或上线状态。

## 标题：概括本次送审的具体结果

让 reviewer 从请求列表中就能辨认变化。优先写具体行为或结果，按需要补充对象和触发条件；重构、构建或文档变更可以直接描述其实际改善，不必虚构用户可见收益。

例如，“防止订单请求并发重试时重复创建订单”比“修复订单问题”更有用；“将日期解析规则集中到同一模块”比“优化代码”更清楚。

标题概括整个送审范围；正文解释原因、机制和取舍。不要用 issue 编号、文件清单或“根据 review 修改”代替变化摘要。格式和长度遵循项目要求，没有要求时保持简短，不机械套字符数。

## 正文：帮助 reviewer 理解和判断

先提供背景、整体目标和具体问题，说明变更后的行为，再补充影响审查判断的机制、理由和证据。按实际需要选择以下内容，不强制填满固定栏目：

- **背景、问题与结果**：这项工作服务于什么使用场景或更大目标，为什么需要这次变更？什么条件下，基线行为有什么问题或限制？应用本次变更后有什么不同？新增能力说明使用场景，重构说明维护负担及需要保持的行为。
- **范围与关键取舍**：解释重要机制、受影响的接口或调用方，以及 diff 中不明显的理由。多个相关 code changes 说明它们如何共同完成目标；必要时交代本次刻意保留的边界。
- **未完成事项**：交代影响目标、范围或交付判断的未做部分，尤其是原计划实现、最终没做成的内容；说明原因、影响和当前处理状态。
- **验证证据**：根据验证内容是否随 code change 提交决定详略：diff 中可见的测试简述覆盖范围，diff 外的验证补充环境、方法、结果和必要证据。
- **风险与交付条件**：有兼容性变化、数据迁移、配置要求、发布顺序或恢复限制时明确写出。只描述实际相关的影响，不为简单变更增加空泛风险清单。
- **审查重点**：确有需要时，指出值得重点检查的契约、取舍或尚待决定的问题，并说明原因。重点提示帮助安排注意力，不将其他受影响部分排除出审查。

涉及界面、交互或性能时，可附有说明的截图、操作步骤或可比较的数据，帮助 reviewer 判断实际变化。链接和附件补充正文，不能替代核心解释；长期维护说明仍应保存在项目文档、代码或测试中。

用明确参照区分基线行为与应用变更后的行为，不仅靠“以前／现在”或语法时态。一次说明清楚即可；版本差异影响证据时，再补具体 commit、环境或时间窗口。

## 验证描述：按 Diff 中是否可见决定详略

### 测试随 Code Change 一并提交

新增或修改的测试已在 diff 中呈现验证方法、场景和断言，正文通常只需一句话概括覆盖了什么，例如“新增并发重试的回归测试”。不逐个解释测试步骤、复制断言或罗列常规通过日志，细节交给测试代码表达。

常见的是单元测试，也可能是集成测试或回归测试；分类依据是验证内容是否随本次变更提交，而不是测试名称。常规测试执行并通过是正常送审的基础，不必作为额外成果反复强调。

### 验证方法没有包含在 Code Change 中

Reviewer 无法从本次 diff 了解这部分验证，需要补足足以理解和核对结果的信息：

- **在哪里验证**：被测版本、环境，以及会影响结果的配置、依赖、数据规模或设备条件。只保留与结论有关的条件。
- **怎样验证**：关键操作、命令或实验方法；使用未提交的脚本或外部测试工具时，说明其作用和必要参数，条件允许时提供可访问的脚本或记录。
- **观察到什么**：实际结果及其支持的结论，按需要附截图、关键输出、日志片段或结果链接。说明证据对应的场景，避免只写“手测通过”或只贴附件；不倾倒完整日志。

这类验证包括特殊环境中的集成检查、手动操作、外部测试系统和性能实验等。无需为了展示证据强行生成截图或日志，但已有且有助于判断的证据应随说明提供。即使测试代码已提交，特殊环境运行得到的、diff 无法表达的结论仍按此方式补充。

### 例外与限制

常规通过可简述，异常和缺口必须明确。未运行、失败、仅部分覆盖，或后续修改使结果不再适用时，说明原因及影响；不能仅因测试代码存在或正在写 review request 就推断测试已通过。缺少执行记录时先核实或说明状态未知，不要求重新运行已有可靠证据支持的测试。

预期效果、本地测试、CI 结果和已部署观测分别表达；旧版本测试通过不能直接写成当前送审版本已通过。

## 没做什么，尤其是想做但没做成的

与 commit message 一样，review request 需要保留理解实际成果所必需的未完成信息。对照原始目标和实际结果，说明有意排除的范围、延期事项，以及尝试后未能实现或被放弃的部分；这些状态不能混写。

对会影响审查判断的缺口，交代原本想达到什么、实际做到哪里、为什么停在这里，以及对验收、使用或发布有什么影响。有后续安排时说明安排，尚未决定时如实写明。不能把没做成的目标悄悄改写为“一开始就不在 scope 内”，也不能只展示成功部分。

失败尝试只保留能解释当前选择、暴露限制或避免重复尝试的结论，无需记录完整过程。没有相关缺口时不凑条目；但已知的重要未完成事项必须披露，不能因模板未设栏目或希望正文简短而省略。

## 简单模板

项目没有指定格式时，可从下列模板起草；已有模板时，将相应内容放入项目栏目。将提示语替换为实际内容，删去不适用的栏目；简单变更可以合并为一两段，不为填满模板增加信息。

```markdown
标题：一句话说明本次送审的具体结果

## 背景与目的

什么场景或问题促成这项工作？希望达到什么结果？

## 本次变更

实际改变了什么？各项变更如何共同完成目标？简述影响判断的关键取舍。

## 未完成事项与影响

哪些目标没做或没做成，为什么？对本次交付有什么影响，后续如何处理？
有兼容性变化、迁移或发布条件时，在这里说明。

## 验证

随 diff 提交的测试：一句话概括覆盖内容。
Diff 外的验证：在哪里、针对什么版本、怎样验证、结果及必要证据。
有未运行、失败或尚未覆盖的重要场景时，说明限制。

## 审查重点

有哪些需要 reviewer 重点判断的事项，为什么？没有特殊重点时省略。
```

## 示例：按需要展开

以下为虚构示例，仅展示写法；实际输出须使用当前变更的事实。

### 简单说明变更

标题：修正快速开始中的配置文件路径

正文：

> 快速开始将配置路径写为 `config/app.yml`，实际示例使用 `config/app.yaml`。本次统一文档中的路径。
>
> 已对照仓库中的示例文件核实路径，并检查相关链接；未运行应用。

### 需要交代整体背景的修复

标题：防止订单请求并发重试时重复创建订单

正文：

> 客户端在创建订单超时后会重试；服务端需要保证同一次下单不会因此创建多个订单。本次将客户端复用请求标识的约定、服务端去重和历史数据检测放在同一送审范围内，共同支持这一目标。
>
> 基线实现先检查请求标识，再插入订单；并发重试可能同时通过检查，创建重复订单。本次使用数据库唯一约束保证同一请求标识只创建一条记录，冲突时返回已有订单。客户端重试需复用原请求标识。
>
> 约束由数据库执行，以覆盖多个服务实例。原计划同时自动清理历史重复记录，但现有数据不足以判断冲突订单中应保留哪一条，未能完成安全的自动清理。本次只提供检测查询；启用约束前仍需确定保留规则并处理存量重复记录，处理方案尚未决定。
>
> 新增覆盖顺序重试、并发重试和不同请求标识的回归测试。
>
> 另在 staging 的双实例环境中验证本次送审版本：使用未提交的请求脚本，以同一请求标识并发发送 100 次创建请求，确认所有响应返回相同订单 ID，数据库中对应记录为 1 条。关键查询输出为 `order_count=1`。尚未在生产数据规模下验证迁移耗时。
>
> 请重点检查冲突路径是否保持原有响应契约，以及历史数据处理是否满足启用唯一约束的条件。

## 变更后更新描述

当实现方案或送审范围变化时，重新检查标题和正文，使首次打开请求的 reviewer 能读到当前完整方案。删除失效结论，替换过时的机制说明，并核对验证证据是否仍适用。原定目标被缩减或放弃时，保留会影响审查判断的原因和缺口，不在重写中抹掉未完成事实。

给已经参与审查的人解释本轮变化时，可以另写简短的更新摘要，说明改了什么、为何调整及补充了哪些验证。正文仍保持当前状态，不追加成返工流水账；必要的决策历史保留在讨论或关联文档中。

## Review Request 写作 Checklist

这份 checklist 检查标题与正文是否准确、有用，不是代码质量、测试执行或合并条件的检查表。用于写作后的自查；是否附在 review request 中遵循项目约定，不默认将它复制进每次正文。涉及条件不适用时标明或跳过，不为勾选编造内容。

- [ ] **形式符合项目要求**：采用了项目要求的语言、标题格式和栏目；模板提示语和空栏目已处理。
- [ ] **标题与范围准确**：标题概括当前完整送审内容，正文与实际 diff 一致，没有把未交付计划写成已完成成果，也没有保留过时方案描述。
- [ ] **Context 足够**：不了解作者会话历史的 reviewer 能理解背景、目的及各项变更的关系；“动机”解释了为什么做。
- [ ] **细节选择有用**：解释了影响整体判断的机制和取舍，没有堆叠 commit messages、文件清单或重复 diff；链接补充而非替代核心说明。
- [ ] **未完成事项透明**：影响判断的未做、没做成和放弃事项已说明原因、影响及当前处理状态，没有将失败目标改写为原定非目标。
- [ ] **验证描述详略合适**：已提交测试只概括覆盖内容；diff 外验证说明了环境、方法、结果及必要证据，读者能判断这些证据支持什么。
- [ ] **事实与限制清楚**：区分了预期、已验证结果和上线观测；验证对应的版本清楚，重要失败、未验证范围和交付条件已披露。
- [ ] **审查诉求明确**：如有重点或待决定问题，已解释需要 reviewer 判断什么及其原因；全文没有无关过程和重复信息。

撰写任务交付可直接使用的标题和正文；审查或改写任务指出具体表达问题并给出修订。仅要求草拟文案时，不执行发布、评论、分支操作或合并。
