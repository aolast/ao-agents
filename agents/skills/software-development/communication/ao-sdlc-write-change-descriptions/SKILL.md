# 编写 Commit Message 与 Review Request

按用户要求选择产物：只写 commit message、只写 review request，或两者一起写。只要求一种时只交付该种，不自动扩展任务。审查或改写文案时指出具体表达问题并给出修订，不据此执行 commit、改写历史、发布请求或评论、开展代码审查或合并。

## 两种写作对象及其互补关系

| 对象 | 解释边界 | 主要阅读需求 |
| --- | --- | --- |
| Commit message | 本提交的具体变化及其持久理由 | 读历史、定位回归、判断是否 cherry-pick，理解为何这样实现以及哪些影响是有意的 |
| Review request | 本次送审目标、各部分关系与交付情况 | 建立整体理解，判断方案、范围、证据和缺口，知道哪些事项需要重点审查 |

Review request 是送审请求，可包含一到多个紧密相关的 code changes。在具体平台使用实际名称，如 GitHub PR、GitLab MR；不以 PR/CR/MR 代指代码变更本身。

“全局”由平台、项目和实际请求的范围决定，可能跨 projects/packages，也可能在 monorepo 内跨 components，或只涉及一个组件。一个提交也可能跨组件，不能按仓库数、文件数或 commit 数机械分工。相关但未包含的工作明确标为外部依赖或后续计划。

Commit 偏细节，review request 偏全局 context，但两者都需要动机与背景。理解提交所必需的理由、重要副作用和未完成边界必须保留在 commit message 中；review request 也应能独立帮助 reviewer 理解整体工作。不能只写“见 PR”或“见 commit message”，允许必要信息重合。

单提交或 squash 合入时，两者范围可能相同。最终 commit message 应解释完整成果并吸收审查形成的重要理由，不能只保留最后一步开发的说明；review request 补充审查导航、当前证据和待判断事项，不把全部评审过程粘贴进最终提交。

## 共同写作原则

### 先确认范围与事实

读取适用的项目约定、实际 diff 和必要背景。Commit message 对照本提交的基线与结果；review request 核对完整送审对象、目标基线和版本，跨项目时分别确认所含变化及依赖。不能只看最后一个 commit，也不能直接拼接开发期间的 messages。

区分已实现内容、计划和未解决问题。动机、实验结果及未完成原因应有依据；缺少材料时先起草已知部分，并核实或明确影响判断的缺口，不编造数据、链接或上线状态。

### 难以写清楚时，检查 Code Change 的 Scope

如果掌握必要背景后，仍很难用清晰的标题和正文解释一个 commit 或 review request，可能是此次 code change 的 scope 有问题。检查是否混入了不相关目标、独立修复或无关重构，或者将机械修改与实质行为变化混在一起，使读者难以判断。写不清楚是检查范围的信号，不是必须拆分的证明；也可能只是表达组织不当。

确有混杂时，提出具体、合理的拆分建议：哪些内容构成一个可理解、可验证的目标，哪些可以独立交付，各部分有什么依赖和先后顺序，以及中间状态是否可用。遵循项目的提交与送审约定，区分拆分 code changes、commits 和 review requests；不按文件数、组件数或文案长度机械拆分，也不把必须共同生效的改动拆开。

例如，修复上传超时的变更夹带全仓库日志格式整理，可以建议将独立整理另行交付；请求封装新增超时参数与上传入口使用该参数则服务于同一目标，无需仅因跨组件而拆开。仅受托写文案时，交付事实准确的草稿，并在文案之外说明范围问题和拆分建议，不擅自修改代码、提交历史或送审结构，也不把尚未实施的拆分写成事实。

### 项目要求优先，形式与内涵分别核对

项目明确要求高于个人偏好及本 skill 模板，包括语言、标题格式、栏目、顺序和必要字段；没有相应要求时参考项目稳定惯例，再采用本 skill 的写法。不默认把某个项目的 Conventional Commits、scope、footer 或平台格式推广到其他项目。

模板通常规定信息放在哪里，写作还要判断内容是否真正回答问题。项目若明确要求实质内容，同样遵守，不能把项目要求一概视为只有形式。例如在“动机”栏中：

- “增加 timeout 参数”只重复了实现动作。
- “使上传能独立设置超时，同时保持普通 API 的失败反馈速度”解释了目的。

将必要信息放入项目对应栏目，不另起一套重复结构。没有“未完成事项”栏目时可放入范围或风险部分；格式简短不能成为隐去重要事实的理由。

### 信息价值与阅读顺序

- **标题可辨认**：写具体对象、触发条件或结果，避免“修复问题”“更新代码”等泛称。Issue 编号可补充，但不能代替有信息的描述。
- **重要信息靠前**：先说明具体问题和本次变化，再展开机制与背景。提供 context 不等于从长篇项目历史讲起。
- **明确前后参照**：用“变更前”“应用本提交后”等表述，不仅依靠时态或孤立的“现在”。版本差异影响判断时补具体版本、环境和时间窗口。
- **解释因果与取舍**：说明为什么值得改、机制如何产生结果、什么约束排除了看似更简单的方案。重构说明维护负担和预期保持的行为，不虚构用户可见收益。
- **让读者找到重点**：大部分 diff 是机械修改时，指出真正改变行为的位置。跨组件时说明接口配合、依赖、兼容性及必要交付顺序，不逐文件复述 diff。
- **保留有效 context**：先摘要有关事实，再链接 issue、设计、相关 commit 或来源。链接和附件补充而非替代核心说明；接口当前用法和长期不变量仍维护在代码或项目文档中。

### 没做什么，尤其是想做但没做成的

对照原始目标与实际成果，区分有意排除、延期、尝试后未完成及放弃的部分。对影响判断的缺口，说明原本想达到什么、实际做到哪里、原因及对使用或交付的影响；有后续安排时交代，尚未决定时如实说明。不能将失败目标事后包装为原定非目标。

同样解释刻意保持的行为、已知副作用及接受理由，以及未采用的明显替代方案。Commit message 保留解释本提交所需的部分；review request 交代整体工作还欠缺什么。失败尝试只保留能解释选择或避免重复尝试的结论，不记完整流水账。没有相关缺口时不凑条目。

### 验证描述：按 Diff 中是否可见决定详略

**测试随 code change 提交**：方法、场景和断言在 diff 中可见，一句话概括覆盖内容即可，不复述测试代码或罗列常规通过日志。常规测试执行并通过是正常送审的基础，不作为额外成果反复强调。区分依据是信息是否随变更提交，而非单元、集成或回归等测试名称。

**验证方法不在 diff 中**：review request 需要补足在哪里、针对什么版本、怎样验证、观察到什么，按需提供截图、关键输出、日志片段或结果链接。只保留影响结论的环境、配置、数据规模和操作；使用外部脚本时说明用途和必要参数，条件允许时提供可访问记录。不能只写“手测通过”或只贴附件，也不倾倒完整日志。已提交测试在特殊环境中得出的额外结论，同样补充这些信息。

Commit message 保留支撑非显然取舍的实验方法、关键条件和结论；当前审查所需的完整日志、截图或临时证据通常留在 review request 或关联记录中。不能因为证据在外部，就删除理解提交所需的结论。

**例外与限制**：未运行、失败、仅部分覆盖或结果已过期时说明原因和影响；不能仅因有测试代码或正在写文案就推断测试通过。区分预期、本地验证、CI 结果和部署观测，旧版本通过不等于当前版本通过。缺少执行记录时核实或说明状态未知，不要求重跑已有可靠证据支持的测试。

## Commit Message：方法与模板

标题概括本提交，正文补充 diff 无法充分表达的动机、前后变化、关键机制、副作用和未包含边界。不能把同任务其他提交的成果算作本提交已完成的内容。临时催审、分工和交接状态不放入 message。

### 个人偏好的格式

没有项目明确要求或稳定惯例时，默认使用不带括号 scope 的 Conventional Commits：普通提交为 `type: description`，不兼容变更为 `type!: description`。不写 `type(scope): description`；需要指出组件或影响范围时，直接写进 description。项目有明确要求时按项目要求，包括项目要求使用 scope 的情况。

Type 使用小写英文，按主要目的选择：`feat` 新功能、`fix` 修复、`refactor` 保持外部行为的重构、`perf` 性能改进、`docs` 纯说明文档、`test` 纯测试、`build` 构建与依赖、`ci` CI 流程、`style` 不影响含义的格式调整、`chore` 其他维护。配套测试或文档不改变功能变更的 type，也不单凭文件扩展名判断类别。

Description 和正文遵循项目语言约定；没有约定时沿用用户任务的语言，保留必要英文术语。标题与正文之间空一行；正文按内容需要使用段落或列表。不兼容变更标 `!`，并在标题或正文说明影响及迁移方式；项目要求额外 footer 时按其要求。

例如 `fix: 修复上传取消后仍显示成功的问题`、`refactor: 集中维护订单可见性规则`，不写 `fix(upload): ...`。不兼容示例为 `feat!: 将订单查询参数从 orderId 改为 order_id`，正文须说明调用方应改用新参数。

### 完整模板与精简写法

以下为完整起草模板。替换提示语，删除无内容的部分，允许合并重复段落；项目格式优先于本模板的默认格式。

```text
type: 能辨认本次具体变化的标题

变更前，说明原有行为、状态或问题。应用本提交后，说明新的行为、状态或结果。

需要这次变化的原因：说明动机及解决的问题。

实现：
- 概括实现结构及重要或不明显的取舍。
- 大部分 diff 是机械修改时，指出真正改变行为的位置。

副作用：
- 已知副作用及其可接受的理由。

未包含：
- 有意未做的相关工作或刻意保持的行为，以及原因。
- 原本想做但未能完成的部分、原因和影响。
- 看似明显却未采用的替代方案，以及原因。

Context：
- 理解本提交所需的事实摘要及 issue、相关 commit、设计或外部引用。
```

精简时让标题承担变化摘要，正文通常用一至三句话保留关键因果、取舍及限制。先删重复、过程记录和易从 diff 看出的动作；重要副作用、未完成边界与验证限制不能为短而丢失。标题已充分解释的简单变更可以没有正文。

正文按语义分段，段落内不按固定列宽手动折行，由阅读工具自动换行；仅保留标题、段落、列表和字段之间有意义的换行。模板与示例中的文案也遵循此规则。项目明确要求物理行宽时服从项目；否则不机械套用 50/72 等字符数规则。Commit message 保持纯文本可读，不依赖表格或富文本渲染。

## Review Request：方法与模板

标题概括整个送审目标。正文使不熟悉作者会话历史的 reviewer 理解：为什么做、各部分如何共同实现目标、已交付与未完成的边界、重要影响，以及有哪些证据和待判断事项。

实现细节只选影响整体判断的部分。必要时给出阅读顺序、截图或可比较的数据；审查重点帮助安排注意力，不将其他受影响部分排除出审查。不要因为有模板，就给简单变更添加无关风险或空栏目。

项目没有指定格式时可用下列模板，已有模板则把相应内容放入项目栏目。替换提示语，删去不适用的部分；简单变更可合并为一两段。

```markdown
标题：一句话说明本次送审的具体结果

## 背景与目的

一句话交代具体问题与本次结果，再补充理解整体目标所需的背景。

## 本次变更

实际改变了什么？涉及哪些部分，它们如何共同完成目标？有跨 project/package/component 的依赖时，说明接口配合、兼容性和交付顺序。简述影响判断的关键取舍；相关但未包含的工作明确标为外部依赖或后续计划。

## 未完成事项与影响

哪些目标没做或没做成，为什么？对本次交付有什么影响，后续如何处理？有兼容性变化、迁移或发布条件时，在这里说明。

## 验证

- 随 diff 提交的测试：一句话概括覆盖内容。
- Diff 外的验证：在哪里、针对什么版本、怎样验证、结果及必要证据。

有未运行、失败或尚未覆盖的重要场景时，说明限制。

## 审查重点

有哪些需要 reviewer 重点判断的事项，为什么？没有特殊重点时省略。
```

## 变更后更新文案

方案或范围变化时，重写标题与正文以反映当前完整成果，删除过时机制与失效结论，核对证据对应的版本。缩减或放弃原目标时保留影响判断的原因和缺口，不在改写中抹掉未完成事实。

给已参与审查的人解释本轮变化，可以另附简短更新摘要；review request 正文仍维护当前状态，不追加成返工流水账。整理最终 commit 时保留重要决策理由，按最终 diff 更新范围；不重新执行提交或发布操作。

## 配对示例

以下场景、版本和证据均为虚构。A、B、C 标识 review request，A1、B1、C1 等标识所含提交，不是真实 commit ID。示例 commit 使用无 scope 的 Conventional Commits，实际格式遵循项目。每组共同事实只写一次，再并列给出两种完整文案；不把示例数字作为真实验证结果。

### 场景 A：文档路径修正，A 对应 A1

共同事实：快速开始写成 `config/app.yml`，仓库示例实际为 `config/app.yaml`；只修正文档，已核实路径与相关链接，未运行应用。

**Commit A1**

```text
docs: 修正快速开始中的配置路径为 config/app.yaml
```

**Review Request A**

```markdown
标题：修正快速开始中的配置文件路径

快速开始将配置路径写为 config/app.yml，实际示例使用 config/app.yaml。本次统一文档中的路径，已对照示例文件核实路径并检查相关链接；未运行应用。
```

Commit 标题已足够说明局部修正；review request 增加简短背景与核实说明，两者都无需填满模板。

### 场景 B：上传超时修复，B 对应 B1

共同事实：B1 修改请求封装、上传入口及超时配置测试，上传超时由 30 秒改为 120 秒，普通 API 不变；服务端缺少幂等保证，原计划的自动重试未实现。Staging 限速实验支持慢速上传改善，但未覆盖移动网络切换。

**Commit B1**

```text
fix: 将文件上传超时从 30 秒调整为 120 秒

变更前，文件上传与普通 API 共用 30 秒超时，较慢网络下的大文件上传可能在完成前被客户端中止。本次为上传请求设置 120 秒超时，普通 API 仍使用 30 秒，以保持原有失败反馈速度。

请求封装新增可选 timeout 参数；实际行为变化只发生在 uploadFile，其他调用继续使用默认值。无响应的上传可能因此多等待最多 90 秒，用户仍可主动取消。

不提高全局超时，以免其他 API 的失败反馈变慢。原计划同时加入自动重试，但服务端缺少幂等保证，未能安全实现；用户手动重试仍可能重复创建文件。本提交只改善超时，不解决重复上传。
```

**Review Request B**

```markdown
标题：减少慢速网络下的大文件上传中断

## 背景与目的

大文件上传可能在客户端 30 秒超时后仍被服务端继续处理，用户无法确定是否应该再次上传。本次将上传超时改为 120 秒，保持普通 API 的超时不变，先改善慢速网络下的上传完成率。

## 本次变更

请求封装支持独立超时，上传入口使用新值，其余调用保持默认值。实际行为变化集中在 uploadFile。无响应上传的等待可能增加最多 90 秒，用户仍可主动取消；不提高全局超时，以免拖慢其他 API 的失败反馈。

## 未完成事项与影响

原计划加入自动重试，但服务端缺少幂等保证，未能安全实现。用户手动重试仍可能创建重复文件，本次尚未解决这一问题。

## 验证

新增默认超时与上传超时配置的测试。

另在 staging 对本次送审版本限速至 1 Mbps，上传 8 MB 文件：基线约 30 秒中止，修改后约 70 秒完成。浏览器网络面板记录显示该上传响应为 201。此结果不代表所有网络条件，尚未覆盖移动网络切换场景。

## 审查重点

请判断 120 秒等待是否符合交互预期，以及现有取消操作能否满足用户退出等待的需要。
```

两份文案覆盖相同代码，关键理由合理重合。Commit 保留超时选择、副作用及不加重试的原因；review request 进一步解释用户处境、外部验证和需要 reviewer 判断的问题。

### 场景 C：订单 CSV 导出，C 对应 C1–C3

共同事实：monorepo 的权限组件、导出服务和管理界面共同实现按当前订单权限导出 CSV。因内存问题未完成大批量导出，当前限制 1 万条；异步导出未实现，后台审计权限保持独立。项目保留三个提交，C1 只重构权限，C2 实现受限导出，C3 提供界面入口。

**Commit C1：准备性重构**

```text
refactor: 提取订单列表与详情共用的可见性判断

将列表和详情接口中的租户、角色及订单归属判断集中到 OrderVisibility，保持两处接口现有的允许与拒绝行为。
```
