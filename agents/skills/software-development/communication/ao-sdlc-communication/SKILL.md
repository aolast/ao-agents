# 共用表达原则

适用于 commit message、design doc、review request 等软件开发写作场景。

### 区分变更内容与送审请求

代码变更本身称为 `code change`（复数 `code changes`）；`review request` 指送审请求，一个请求可以包含一到多个紧密相关的 code changes。不要用 PR/CR/MR 代指代码变更或实现工作；在具体平台语境中保留实际名称，如 GitHub 的 PR、GitLab 的 MR。

示例：“这个 code change 为重试请求增加去重处理，已通过 GitHub PR #42 提交审核。”

### 用目标分支描述合入位置

描述 code change 的合入位置时使用“目标分支”（target branch），不用 `mainline` 代指。提到具体分支时使用实际名称；目标分支、仓库默认分支和 `main` 等具体分支名不是同义词。

示例：“该 code change 将合入目标分支 `release/2.4`；仓库默认分支为 `main`。”

### 遵循项目的语言与格式约定

采用目标项目明确的语言和格式约定；没有约定时以清晰、简短的事实表达为准。代码、命令参数、标识符和原文引用保留实际写法。

示例：项目要求 design doc 用中文时，可写“使用 `request_id` 识别同一次请求的重试”，字段名保持原样。

### 明确前后版本参照，不靠时态区分

用明确的版本或变更参照区分基线行为与应用该 code change 后的行为，不用语法时态承担这一区分，也不要只靠“现在／以前”。一次明确参照后可以自然续写，不必每句话附 SHA；多轮修订、复现或部署差异影响判断时，再补精确版本。

- 参照不清：“现在不会重复写入了，以前会失败。”
- 参照清楚：“基线版本在请求重试时可能重复创建记录；应用该 code change 后的版本复用请求标识去重。”

### 区分预期、验证结果与运行事实

分别说明预期结果、已验证结果和实际运行中的观测，不把计划或推测写成已完成的事实。描述运行观测时，明确对应的已部署版本、环境和时间窗口。

示例：“该方案预期减少重复写入。新增回归测试已通过；生产部署状态尚未确认。”
