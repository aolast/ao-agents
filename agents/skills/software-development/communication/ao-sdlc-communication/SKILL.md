# 工程沟通与写作

## 术语与语言

- **Code change**：描述代码变更本身时使用 `code change`（复数 `code changes`），不用 PR/CR/MR 代指代码变更或实现工作；例如“完成这个 code change”。
- **Review request**：`review request` 是送审请求的抽象概念，一个请求可以包含一到多个紧密相关的 code changes；区分变更内容与承载它的评审请求。
- **平台叫法**：在具体平台或团队语境中沿用实际名称，例如 GitHub 的 PR、GitLab 的 MR，以及公司内部系统的叫法；无需统一替换成 review request。编号、命令和原文引用保留实际名称。
- **项目约定**：采用目标项目的语言和格式约定；没有约定时以清晰、简短的事实表达为准。

## 版本与断言

- **明确前后参照**：用明确的版本或变更参照区分基线行为与应用该 code change 后的行为，不用语法时态承担这一区分，也不要只靠“现在／以前”。
- **基线**：按需要说明该 code change 相对于哪个基线版本（base），其行为是什么。
- **变更结果**：说明应用该 code change 后的版本（head）改变了什么行为。
- **运行事实**：描述运行观测时，明确对应的已部署版本、环境和时间窗口。
- **意图与证据**：区分预期结果、已测试结果，以及仍属推测或待验证的内容。
- **参照精度**：一次明确参照后可以自然续写，不必每句话附 SHA；多轮修订、复现或部署差异影响判断时，再补精确版本。时间词可以使用，但参照应清楚。

## 组织内容

- **读者需要**：先确定读者要理解什么或作出什么决定，再选择必要信息。
- **信息顺序**：先写问题或结果及其影响，再解释必要的原因、机制和证据。
- **引用上下文**：引用 issue 或资料时摘要说明相关事实，不要求读者先通读长讨论。
- **设计说明**：交代目标、关键约束、采用方案及理由，以及如何判断成功。
- **Commit message / review request**：交代变更动机、具体影响、关键实现理由、验证与实际限制。
- **评审意见**：说明版本或位置、触发条件、具体后果和依据。
- **进度更新**：说明已得到的结果、尚缺的信息或证据，以及接下来能解决缺口的行动。
- **必要细节**：不罗列所有文件和工具调用，不用形容词代替效果；只展开帮助读者判断的细节。

## 信息归属与核对

- **长期维护信息**：接口契约和维护不变量放在代码、测试或项目文档。
- **过程与接续信息**：短期评审对话留在讨论中，接手状态放在工作记录中；需要避免重复高成本调查的结论可保留并链接，无需复制整段过程。
- **事实核对**：正文完成后核对事实来源、版本和验证状态；不要把计划写成完成，把本地测试写成线上验证，或把审查建议写成已接受的需求。

## 表达示例

- 参照不清：“现在不会重复写入了，以前会失败。”
- 参照清楚：“基线版本在请求重试时可能重复创建记录；应用该 code change 后的版本复用请求标识以去重。新增回归测试已通过，生产部署状态尚未确认。”
