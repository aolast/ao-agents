# 工程沟通与写作

先确定读者要理解什么或作出什么决定，再选择必要信息。采用目标项目的语言和格式约定；没有约定时以清晰、简短的事实表达为准。

## 版本与断言

描述代码行为时明确参照，尤其不要只靠“现在／以前”或语法时态区分变更前后。[Simon Tatham 的文章](https://www.chiark.greenend.org.uk/~sgtatham/quasiblog/commit-messages/) 对这一歧义及读者视角提供了具体分析。

按需要分别写清：

- **基线**：本变更相对于哪个版本或 PR base。
- **变更结果**：这份 diff 或 head 增加了什么行为。
- **运行事实**：哪个已部署版本、环境和时间窗口出现了什么观测。
- **意图与证据**：预期结果是什么，哪些已测试，哪些仍是推测或待验证。

不是每句话都附 SHA；一次明确参照后可以自然续写。多轮修订、复现或部署差异影响判断时，再补精确版本。把相对时间换成参照清楚的表达，不必机械禁用所有时间词。

## 组织内容

先写问题或结果及其影响，再解释必要的原因、机制和证据。标题让读者分辨这次具体变更，正文补充代码 diff 难以表达的信息。引用 issue 或资料时摘要说明相关事实，不要求读者先通读长讨论。[Michael Lynch 的文章](https://refactoringenglish.com/excerpts/commit-messages/) 说明了这种信息组织及验证限制披露的价值。

| 场景 | 优先回答的问题 |
| --- | --- |
| 设计说明 | 要解决什么、关键约束、采用什么方案、为什么、如何判断成功 |
| Commit / PR / CR | 为什么需要变更、具体影响、关键实现理由、验证与实际限制 |
| 评审意见 | 哪个版本和位置、什么条件下有什么后果、依据是什么 |
| 进度更新 | 已得到什么结果、还缺什么、接下来什么行动能解决它 |

不罗列所有文件和工具调用，不用形容词代替效果。重要信息先呈现，细节只有在帮助读者判断时才展开。

## 信息放在哪里

长期生效的接口契约和维护不变量放在代码、测试或项目文档；提交消息解释这次变化及理由。短期评审对话留在讨论中，接手状态交给 [work-log](../../work-log/ao-sdlc-work-log/SKILL.md)；需要避免重复高成本调查的结论可保留并链接，而非复制整段过程。

正文完成后核对事实来源、版本和验证状态。不要把计划写成完成，把本地测试写成线上验证，或把审查建议写成已接受的需求。

Commit 格式、是否使用 Conventional Commits、是否允许 scope 均读取目标仓库规则。本 skill 不把 Ao Agents 的提交格式推广到其他项目。

## 表达示例

参照不清：“现在不会重复写入了，以前会失败。”

清楚的写法：“PR 基线在请求重试时可能重复创建记录；该变更复用请求标识以去重。新增回归测试已通过，生产部署状态尚未确认。”

简单拼写修正只需说明纠正了什么；无需额外编造用户影响、替代方案或长篇背景。
